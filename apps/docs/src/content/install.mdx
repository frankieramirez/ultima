# Install

Ultima ships as a shadcn-compatible registry. You copy source into your project with the CLI and own it after that.

Start with `init`. It sets up a new or existing Vite or Next.js App Router application in one reviewed step. The walkthrough after it does the same by hand, for every project `init` does not cover.

Already using Ultima? Read [Update the base theme](/install/update) before reinstalling tokens. It explains the Neutral/Tight change and how to keep the previous appearance.

<Callout icon={<InfoIcon />} title={<><Code>npx shadcn init</Code> is not supported.</>}>Its preflight requires Tailwind on disk, and Ultima does not use Tailwind. The entry is a per-target setup item, which is a universal `registry:item` and installs into a project that has no `components.json` yet.</Callout>

## Set up with init

```bash title="Terminal"
npx ultima-design@latest init my-app --framework vite
npx ultima-design@latest init my-next-app --framework next --layout src
npx ultima-design@latest init .
```

**A new directory.** `init` runs the framework's own scaffold in a private staging directory. It installs the setup item with Button, Card and Dialog, wires the compiler and resets, and puts a small preview on the home route. The directory appears only after the setup checks and the production build pass.

**An existing application.** `init` detects the framework, layout and package manager, then plans only what is missing. Your pages, providers, root documents and theme files stay as they are. The preview goes on its own route in Next.js; in Vite, the report tells you where to mount it.

**Review first.** Before anything is written, `init` shows every dependency, file diff and command, and asks in a terminal. Elsewhere, save the plan, read it, then apply it unchanged:

```bash title="Terminal"
npx ultima-design@latest init . --plan --json > ultima-init-plan.json
npx ultima-design@latest init --apply ultima-init-plan.json
```

**Agent setup.** The CLI's `install` writes the skill and post-edit hooks for the harnesses it detects, or the ones you name with `--harness`. `init` hands that step to it only when the application is the root of its Git repository, because the hooks run from that root. A new project has no repository, and `init` never creates one, so the report prints the commands for later. A project nested in another repository wires its hook by hand.

**The report.** It names the files created, edited and preserved, the resolved versions, the logs, and each check, including the production build. It says whether the preview is mounted and that no browser check ran. Each step left to you names its file, the edit and how to verify it.

**Recovery.** In an existing application, `init` saves the original of every file before it writes. If a run stops, running `init` again plans only what is left. The report prints the command that undoes the run, `npx ultima-design init . --rollback <run-id>`, which restores only the files nobody changed since.

Yarn, Bun, workspaces, the Pages Router and JavaScript-only projects are not automated yet. Set them up by hand below.

**Why resets need a layer.** Every StyleX rule sits in a cascade layer, so an unlayered reset such as create-next-app's `* { padding: 0 }` beats component styles, including a Button's own padding.

```css title="src/index.css · app/globals.css"
@layer reset {
  *,
  *::before,
  *::after {
    box-sizing: border-box;
  }

  body {
    margin: 0;
  }
}
```

**Only if you follow the Data Table recipe.** `@tanstack/react-table` v9 is ESM-only. It ships no CJS and no UMD build and declares `engines.node >= 20`, so a toolchain that `require()`s it cannot load it: a CJS config path, or a test runner without ESM support. Nothing else Ultima documents asks this of you, and Ultima does not pin the last dual-published major to buy CJS back — it is more than a year old, and a toolchain that cannot resolve ESM cannot compile StyleX either.

## StyleX lint

The StyleX compiler can accept styles that are not valid, so [StyleX recommends its ESLint plugin](https://stylexjs.com/docs/learn/installation/#eslint). Ultima ships the plugin's configuration as one file. Download [`ultima.eslint.mjs`](/ultima.eslint.mjs) and save it next to `eslint.config.mjs`. From then on the file is yours. Setup items never write an ESLint config and never install ESLint.

```js title="ultima.eslint.mjs"
// Ultima's StyleX lint fragment for an ESLint 9 flat config: https://ultima.systems/install#stylex-lint
// Save it beside eslint.config.mjs; you own it from then on. Append `ultimaStylex` to your config array
// after your framework's configuration, and put your own overrides after it.
// Tested with eslint 9.39.5, typescript-eslint 8.71.1 and @stylexjs/eslint-plugin 0.19.1.
import stylex from '@stylexjs/eslint-plugin';

export const ultimaStylex = {
  name: 'ultima/stylex',
  files: ['**/*.{js,jsx,mjs,cjs,ts,tsx,mts,cts}'],
  plugins: { '@stylexjs': stylex },
  rules: {
    '@stylexjs/valid-styles': ['error', { allowOuterPseudoAndMedia: true }],
    '@stylexjs/no-unused': 'warn',
    '@stylexjs/valid-shorthands': 'warn',
    '@stylexjs/no-conflicting-props': 'warn',
    '@stylexjs/sort-keys': 'off',
  },
};
```

Invalid styles are errors. `allowOuterPseudoAndMedia` accepts the namespace-level `':hover'` and `@media` blocks that installed components use. Unused styles, shorthand advice and conflicting props are warnings. Key order is your choice, so `sort-keys` is off, and so is every other upstream rule.

**A project without ESLint.** This includes a create-vite app, which ships oxlint. Install the tested versions:

```sh title="Terminal"
npm install -D --save-exact eslint@9.39.5 typescript-eslint@8.71.1 @stylexjs/eslint-plugin@0.19.1
```

Then create the config. It parses TypeScript and JSX syntax only. It adds no type-aware linting and no general TypeScript rules.

```js title="eslint.config.mjs"
import tseslint from 'typescript-eslint';
import { ultimaStylex } from './ultima.eslint.mjs';

export default [
  { ignores: ['**/node_modules/**', '**/dist/**', '**/.next/**', '**/out/**', '**/coverage/**'] },
  {
    files: ultimaStylex.files,
    languageOptions: {
      parser: tseslint.parser,
      parserOptions: { ecmaFeatures: { jsx: true } },
    },
  },
  ultimaStylex,
];
```

If `package.json` has no `lint` script, add `"lint": "eslint ."`. If it already runs another linter, such as create-vite's oxlint, keep that linter and run ESLint after it: `"lint": "oxlint && eslint ."`.

**An existing ESLint 9 flat config.** Install only the plugin, `npm install -D --save-exact @stylexjs/eslint-plugin@0.19.1`, and keep your parser, rules and ignores. Import the fragment and put it after your framework's configuration. In a create-next-app project with ESLint, that looks like this:

```js title="eslint.config.mjs"
import { ultimaStylex } from './ultima.eslint.mjs';
import { defineConfig, globalIgnores } from 'eslint/config';
import nextVitals from 'eslint-config-next/core-web-vitals';
import nextTs from 'eslint-config-next/typescript';

const eslintConfig = defineConfig([
  ...nextVitals,
  ...nextTs,
  ultimaStylex,
  globalIgnores(['.next/**', 'out/**', 'build/**', 'next-env.d.ts']),
]);

export default eslintConfig;
```

Put your own rule overrides after `ultimaStylex`, where they win. If your config already registers `@stylexjs` from `@stylexjs/eslint-plugin`, keep it: the fragment registers the same plugin object, so ESLint accepts both. If you registered a different object under that name, use one object and merge the rules into it. ESLint 8 legacy configs and ESLint 10 are not verified. Ultima does not migrate them.

**Check the effective config.** Run each command from the package that holds `eslint.config.mjs`:

```sh title="Terminal"
npx eslint --print-config src/App.tsx
npx eslint .
npx ultima-design doctor
npx ultima-design check
```

`ultima-design doctor` lists what it can see under **StyleX lint**: a missing package or config, an unverified ESLint or plugin version, an ignored component, or `detected`. It reads files and installed versions only. It never runs ESLint, so `detected` is not a lint pass, and its lint advice never changes doctor's exit code.

For Next.js, probe the page under `app/` or `src/app/` instead. Also probe an installed component and the token and theme modules in your lib folder. Each should name the typescript-eslint parser and show `@stylexjs/valid-styles` at severity 2. A file that prints `undefined` is ignored, and an ignored component means lint does not cover it.

ESLint exits 0 when it reports only warnings, 1 when it reports errors and 2 when it could not run. Run the lint script once in CI, without `--fix` and without `--max-warnings 0` unless your project already wants that. Review autofixes locally. After installation, every command uses local packages and runs offline. `ultima-design check` never runs ESLint, and passing lint does not mean the build applied your theme.

## Tokens without StyleX

Components need a StyleX compiler. Tokens do not.

The stable URL is `https://ultima.systems/tokens.css`. Mana's audit report fetches or vendors that file and inlines it. The `tokens-css` registry item writes the same generated stylesheet to `~/ultima-tokens.css` if you want it committed next to your source.

The export is plain CSS, with no imports, no URL references, and no remote fonts. It follows the system color scheme on `:root` and also ships `[data-theme="dark"]` and `[data-theme="light"]` blocks, so an attribute on the root element pins a document to one mode.

## Web components

Nine components also ship as custom elements for a host that cannot run React, installed the same way as a registry item (`npx shadcn add @ultima/ult-button`) or loaded from `https://ultima.systems/elements/`. The [Elements](/elements) page has both paths and the styling story.

## For an agent

`init` sets up the skill and hooks through the consumer CLI, as described above. To add them later, or to a project you set up by hand, install the `ultima-design` skill through skills.sh, the Ultima marketplace in Claude Code, or the consumer CLI. The [CLI page](/cli#other-skill-installers) lists the commands and explains which route also installs post-edit hooks. GitHub installation requires repository access until Ultima becomes public.

Before UI edits, the skill asks your agent to read applicable project instructions and local design guidance, then trace the active theme at each affected boundary. It links the hosted [discovery and safe-update workflow](/llms.txt#discover-and-maintain-the-product-theme), including conflicts and offline work. The guide also contains conventions and component APIs. When the host is unavailable, use known guidance and installed source, report the gap, and run the pinned local CLI with `npx --no-install ultima-design doctor` and `npx --no-install ultima-design check`. Registry comparisons remain unverified offline.

## Theme adoption

Keep Neutral in a fresh project until you choose a theme. For an existing brand, record its semantic roles, font faces, spacing, shape and mode behavior before an authorized change. Preserve those choices in a custom [Theme Studio](/theme-studio) draft. Selecting another preset requires an explicit project choice.

[Theme Studio](/theme-studio) generates a theme for an existing Ultima application. Download the registry file, then run:

```sh title="Terminal"
npx shadcn add ./ultima-theme.registry.json
```

The registry installs `ultima-theme.css`, `ultima-theme.json`, and `DESIGN.md` at the project root. Keep the JSON draft for later editing. The design document describes the current draft for people and agents. Reinstalling replaces whole files through the installer's overwrite prompt. Review the diff and preserve consumer prose; for linked maintenance, stage the generated region and reconcile hand edits before replacement using the [safe-update workflow](/llms.txt#discover-and-maintain-the-product-theme).

To start with Ultima's default design document on its own, run `npx shadcn add @ultima/design-md`. Review the file for your application and update it when you change the theme.

Import the stylesheet after your application's StyleX output. For Vite, in `src/main.tsx`:

```tsx title="src/main.tsx"
import './index.css';
import '../ultima-theme.css';
```

For Next.js, in `app/layout.tsx`:

```tsx title="app/layout.tsx"
import './ultima.css';
import '../ultima-theme.css';
```

For Next.js with `src/app/layout.tsx`:

```tsx title="src/app/layout.tsx"
import './ultima.css';
import '../../ultima-theme.css';
```

Set `data-theme="dark"` or `data-theme="light"` on `html` to select a mode. Remove the attribute to follow the system preference. The generated CSS sets `color-scheme` and respects reduced motion. It exports font stacks; load your preferred font faces yourself or use the fallbacks.

The optional StyleX export contains all token groups. Apply both `ultimaTheme.dark` and `colorScheme.dark` to a dark scope, or their light equivalents to a light scope. Put the portal containers for Select, Dialog, Popover and other popups inside that scope. A popup attached to `document.body` inherits the document theme instead.

Run `npx ultima-design doctor` and `npx ultima-design check`, then compare your production build with the Studio preview. Check the root, an Ultima control and an open popup in dark, light and system mode, including focus, disabled states and reduced motion. The commands cannot prove that the browser applied the stylesheet.
