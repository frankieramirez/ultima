# Rendered consumer proof

Decided on [Decide the rendered consumer proof required for a production recommendation](https://github.com/frankieramirez/ultima/issues/617). Status: accepted for implementation. This is a plan, not evidence that the current repository passes it. [Ultima's principles](ultima.md#principles), [the theme-adoption decision](https://github.com/frankieramirez/ultima/issues/616), [Theme Studio's export contract](theme-studio.md#theme-export-installation-and-recovery), and [the browser-support decision](https://github.com/frankieramirez/ultima/issues/618) set the boundaries. The existing [registry smoke install](ultima.md#the-registry-smoke-install), component suites and Studio parity tests remain required.

## Fixture and provenance

Build one small application scene from *installed* registry items in disposable consumer projects. The same scene runs in the documented Vite React layout and Next App Router with both root and `src/` layouts. It has a labelled form with a required field, selection and submit/reset result; navigation with a current route and a keyboard-reachable destination; a portalled Dialog or Select; and data content with a meaningful row or empty state. Use real Ultima controls and a non-stock, passing Studio draft whose resolved values differ from Neutral and Ultima in both modes. Use semantic token expectations generated from that draft, never hand-maintained color literals. The scene must show at least one accent control, focus indicator, status role and painted surface so an absent or losing stylesheet fails observably. Keep fixture data deterministic and network-free.

Scaffold each project afresh outside the Ultima workspace. Serve the registry build over loopback, install setup and only the scene's component dependencies through the documented shadcn flow, and run the hand steps printed by setup. Build each project in production mode and serve that output; Next tests must load the server-rendered page and hydrate it in a real browser. Record the exact source commit and registry manifest hash, generated draft fingerprint and recipe version, framework and browser versions, installed item list, CLI tarball digest, and command line with each report. The fixture must use consumer aliases and CSS import order as generated by the setup path. Do not import `packages/ui`, `packages/tokens` or Studio source by workspace alias into the fixture.

## Delivery paths

Use the same draft and scene for four delivery checks:

1. **Generated CSS, primary path.** Install the local theme registry item, retain its draft JSON, import `ultima-theme.css` after the base StyleX output, and exercise system preference plus explicit dark and light `data-theme` on the document root. Assert the installed files and imports, then run the browser obligations below. This is the primary Vite and both Next-layout path.
2. **Compiled StyleX, subtree path.** Put the generated module in a compiler-included consumer path, apply every complete group theme and `colorScheme` on a subtree, and mount its portal container inside that subtree. Assert that its compiled values match the draft and that the portal inherits this subtree instead of the document theme. Test the consumer alias and compiler setup in Vite and both Next layouts. A missing extraction or partial group application fails.
3. **Registry installation.** Install the downloaded self-contained theme item with shadcn in a fresh project, verify both emitted theme files and the draft fingerprint, and compare its computed values with the direct generated CSS result. Do not copy files into the fixture as a substitute for this check. The primary path can satisfy this obligation when it truly uses that install route; do not duplicate its browser matrix.
4. **Packed CLI.** Install the `pnpm pack` tarball into the disposable project from its own dependencies. Run `ultima-design doctor` and `check` against each layout and require successful, complete reports. This establishes consumer setup and source rules alongside the browser result; a CLI pass alone is not rendered proof.

Keep the existing Studio preview/CSS/StyleX parity corpus for stock, shuffled, overridden and acknowledged failing user drafts. The integrated proof uses a shipped passing draft and tests actual installation, extracted production CSS, alias resolution, cascade, portals and hydration. Preset revisions also follow [the complete preset release bar](theme-studio.md#release-bar-and-consumer-guidance): every shipped preset must pass its own two-mode pairing and installed-consumer parity checks. Reuse this fixture and its assertions rather than multiplying application scaffolds for each preset.

## StyleX lint proof

The [consumer lint contract](consumer-lint.md), decided on [Decide the StyleX linting contract for consumer projects](https://github.com/frankieramirez/ultima/issues/730), adds official StyleX lint to the same installed Vite and Next root/src fixtures. Run the project's local lint command once per immutable layout build before production compilation, alongside packed CLI doctor/check. Retain effective-config probes, exact plugin/ESLint/parser versions, file coverage and positive/negative diagnostics. Prove absent-config setup, preservation of existing rules/ignores and offline execution. Static doctor detection is not an executed lint pass. Reuse this result across browser/mode cells; the 54-cell browser matrix and rendered obligations stay unchanged. This addition is pending implementation.

## Browser pass conditions

Run the shared scene in production browsers, using the 54-cell cross-engine matrix and its framework/element split settled on [the browser-support decision](https://github.com/frankieramirez/ultima/issues/618). This fixture supplies the Vite and Next cells; the element lifecycle cells keep their own light-DOM fixture. A cell passes only when all applicable assertions below pass in both dark and light. The system-preference check additionally changes the emulated preference without an explicit attribute, then forces each explicit mode to show that it overrides the preference.

- **Real paint and parity:** the app root, accent control, status content and open portal have nontransparent or otherwise observable computed paint where their contract calls for it. Compare representative computed semantic variables, `color-scheme`, background, text, border and focus styles to the resolved draft and across CSS/StyleX/registry outputs. Verify that the non-stock sample actually differs from Neutral/Ultima on chosen roles. Compare shadows and font-stack strings where present; do not mistake an unloaded preferred face for a token mismatch.
- **Navigation and form:** keyboard navigation reaches the destination and current state updates. Form labels and errors have accessible names; required validation, selection, submit and reset produce the expected visible state and serialized values. Assert the installed data content's expected row and empty-state transition. Exercise both pointer and keyboard activation on at least one control.
- **Overlay and focus:** opening the portal exposes the right role and name, places focus inside it, keeps its computed theme values and `color-scheme` equal to its intended root or subtree, supports keyboard action and Escape, and restores focus to the trigger. Confirm the popup is actually portalled and that its open state is included in accessibility checks.
- **Hydration and motion:** compare the server HTML's initial mode and visible content with the hydrated Next page. Require no hydration warning, React error, uncaught page error, failed required asset, or missing StyleX extraction. Switch modes after hydration and assert values change without stale portal styling. With reduced motion enabled, assert the export's fixed fast/base/slow collapse and loop value through computed styles while interaction remains usable.
- **Accessibility:** run axe on the rendered scene with the overlay closed and open in both modes. The token pairing gate remains separate; a passing axe run does not replace computed theme, keyboard or hydration assertions.

Every assertion must target a stable role, accessible name, test ID for a value probe, or a known semantic token. Do not bless a screenshot as the sole oracle. On failure, retain the fixture directory, build and server logs, browser console/page errors, failed requests, accessibility report, screenshot and a JSON snapshot of expected versus computed values with mode, engine, layout and delivery path. Include the exact failing command so a developer can reproduce one cell. A missing or incomplete report is a failure, not a pass.

## Gates and cost

Relevant PRs run the affected installed-consumer cases and delivery paths when setup, tokens, theme resolution/export, registry metadata, components used by the scene, StyleX configuration, CLI or the verifier changes. Shared resolver, runner, browser configuration or dependency changes run the full shared matrix. Unknown dependency impact expands to the full matrix rather than silently skipping a case. Keep the existing full-catalogue smoke install trigger and checks. Use one scaffold per layout and reuse it across mode/browser assertions; cache immutable package downloads, not installed source or generated output being tested. Report warm-CI time and tune selection against the browser-support decision's initial 15-minute additional budget, without dropping a required assertion to meet it.

A release recommendation requires the full shared 54-cell browser matrix, all four delivery obligations, the existing smoke install, Studio pairing/parity gates and `pnpm verify release` green on the same source revision. Record the report IDs and artifact hashes. A failed preset revision blocks a recommendation for that preset and any release that includes it. Weekly runs and dependency/browser upgrades refresh the complete evidence; stale reports do not prove a changed build.

The local loopback fixture proves a reproducible installed application. The separate live-domain stranger-path check already required by [the public launch effort](https://github.com/frankieramirez/ultima/issues/587) must fetch the public registry and documentation without repository or local-build shortcuts and verify the promoted artifact and theme in a fresh consumer. Record the public URL, fetched artifact hashes, install commands and browser result. It gates a public production claim and promotion, not ordinary PRs. A green local report cannot stand in for it. This plan neither publishes the repository nor authorizes a site or package release.
