# Rendered consumer proof

Decided on [Decide the rendered consumer proof required for a production recommendation](https://github.com/frankieramirez/ultima/issues/617). Status: accepted for implementation. This is a plan, not evidence that the current repository passes it. [Ultima's principles](ultima.md#principles), [the theme-adoption decision](https://github.com/frankieramirez/ultima/issues/616), [Theme Studio's export contract](theme-studio.md#theme-export-installation-and-recovery), and [the browser-support decision](https://github.com/frankieramirez/ultima/issues/618) set the boundaries. The existing [registry smoke install](ultima.md#the-registry-smoke-install), component suites and Studio parity tests remain required.

## Fixture and provenance

### Implemented generated-CSS runner

`node --experimental-strip-types scripts/consumer-proof.ts --layout <vite|next-app|next-src> --delivery-path <css|stylex-subtree|registry|cli>` installs the same non-stock draft and the Projects screen in a fresh external production app. The scene is the screen's consumer-copy bundle from [the composition inventory](screen-composition.md#bounded-example-inventory), written to `components/projects/` and installed by its derived `npx shadcn add` command; the runner adds only a wrapper for mode tracking, the subtree theme and its portal container. The verifier registers every layout and delivery path. Every Chromium cell exercises pointer and keyboard form/selection, submit/reset, current-route navigation, data/empty-state restoration, one column at 390px and side-by-side columns at 1280px without document overflow, keyboard scrolling of the narrow table, portal focus entry and return, live explicit/system mode switching, reduced-motion values and interaction, and axe with the overlay closed/open in the initial and opposite mode. The installed-consumer CI workflow runs the cells a pull request's change plan selects, per [Gates and cost](#gates-and-cost), and retains source manifests, commands, consumer sources, values, screenshots and Next server HTML for 90 days on every run, passing or failing.

Every path installs the theme item through shadcn and verifies the emitted CSS and JSON against the draft. The subtree path compiles the generated StyleX module under the consumer alias, applies all eight group themes and its color scheme, and places the actual Dialog portal inside that subtree. Each case compares every resolved token on the intended root, control and portal, plus paint and extraction. Packed CLI JSON reports retain executed doctor/setup and check/scope results. The registry path first builds a direct generated-CSS reference, compares its non-stock installed result with that reference, and then reuses its scaffold for every shipped preset, including explicit/system modes, portal inheritance, keyboard focus and reduced motion. The reference is not a registry installation and cannot satisfy the installed cases. The old hand-written `smoke-theme.ts` fixtures are retired.

`--fault portal-theme`, `--fault required-error-name` and `--fault focus-return` mutate the installed scene's portal boundary, required-field error name and Dialog focus-return behavior. Each must build successfully and fail its browser assertion. Every case retains its copied fixture, build/server logs, console/page errors and failed requests, four axe reports, screenshot and expected/computed JSON. The JSON and adjacent `.reproduce.txt` carry the source revision and exact command with `--case <cell-id>`. That option selects only the named cell; registry reproduction also builds its required direct-CSS comparison reference. A selected-cell report cannot satisfy a full-matrix verifier request.

Next root `app` and `src/app` use the printed setup steps, including moving the extraction marker into `src/app`. The generated theme import follows that marker. The fixture's explicit initial mode comes from a request cookie; its root layout intentionally renders per request (`instant = false` on Next versions with Cache Components), so the server HTML includes the chosen mode. A JavaScript-disabled page captures the server content and mode attributes; a fresh browser context then hydrates the same request. Missing hydration completion, content or mode drift, console errors, hydration warnings, uncaught errors and failed required assets fail the case. Button height and radius come from the resolved token table; display and paint prove extraction.

The runner's `--base-styles <built-app>` case also preserves the catalogue smoke's stock assertions in Vite and both Next layouts: source-derived Button height, Tight radius, neutral accent and keyboard focus, and danger paint in both modes. `smoke-install.sh` calls this case against its existing production builds, with values and screenshots retained beside each app. It does not scaffold a second stock matrix.

`--layout next-src --fault src-extraction` excludes the `src` tree from PostCSS extraction. `--fault hydration-mismatch` makes the probe's server and client content disagree in either Next layout. Both faults must finish the production build and fail the browser cases, with per-mode values snapshots. The existing Vite theme-import and extraction fault switches remain available. `smoke-install.sh` retains its catalogue-breadth builds and CLI checks; its standalone Next rendered-style script has moved into these runner cases.

Build one small application scene from *installed* registry items in disposable consumer projects. The same scene runs in the documented Vite React layout and Next App Router with both root and `src/` layouts. It has a labelled form with a required field, selection and submit/reset result; navigation with a current route and a keyboard-reachable destination; a portalled Dialog or Select; and data content with a meaningful row or empty state. Use real Ultima controls and a non-stock, passing Studio draft whose resolved values differ from Neutral and Ultima in both modes. Use semantic token expectations generated from that draft, never hand-maintained color literals. The scene must show at least one accent control, focus indicator, status role and painted surface so an absent or losing stylesheet fails observably. Keep fixture data deterministic and network-free.

Scaffold each project afresh outside the Ultima workspace. Serve the registry build over loopback, install setup and only the scene's component dependencies through the documented shadcn flow, and run the hand steps printed by setup. Build each project in production mode and serve that output; Next tests must load the server-rendered page and hydrate it in a real browser. Record the exact source commit and registry manifest hash, generated draft fingerprint and recipe version, framework and browser versions, installed item list, CLI tarball digest, and command line with each report. The fixture must use consumer aliases and CSS import order as generated by the setup path. Do not import `packages/ui`, `packages/tokens` or Studio source by workspace alias into the fixture.

### Cross-engine bundles

`node --experimental-strip-types scripts/consumer-proof.ts --layout vite --delivery-path css --exercise bundles [--engine <chromium|firefox|webkit>]...` runs the first three [production bundles](consumer-support.md#bounded-production-proof) on the canonical Vite fixture: theme and CSS, overlay and keyboard, and form, each in dark and light, in Chromium, Firefox and WebKit. That is 18 cells. `--engine` narrows the run to the named engines; without it every engine runs. The fixture is the Projects scene plus probes the scene lacks: a layered reset, a disabled Button, a popup portalled into each of a dark and a light `data-theme` scope, a Select inside an `overflow: hidden` box, and a form with uncontrolled, controlled, read-only and disabled inputs, a Checkbox and a Select. The runner builds it once, serves the output once, and runs each engine's cells two at a time in fresh contexts. `scripts/consumer-report.ts` holds the case registry (`bundleCases`, IDs `vite/bundles/<engine>/<bundle>-<mode>`) and `scripts/consumer-bundles.ts` holds each bundle's assertions. Each cell records every assertion's expected and actual value, and retains its browser log and screenshot. A failed cell also keeps a Playwright trace. A cell that runs past its bundle's deadline fails. An engine that cannot launch leaves its cells unexecuted, and the run is incomplete with the reason recorded. The report records each engine's version, the operating system, the hash of the served build and the lockfile digest, and every cell repeats them. `--fault portal-theme` must fail the theme cells in every engine. The verifier registers the run as `consumer-bundles-vite`, and the installed-consumer workflow runs it in one job after installing all three engines.

### Next hydration and element cells

`--layout <next-app|next-src> --exercise bundles` runs the Next layouts' hydration bundle on the Projects scene in each engine and mode: 12 cells, IDs `<layout>/bundles/<engine>/hydration-<mode>`. Each cell asks the server for its mode through the proof cookie against the opposite system preference. It captures the server HTML with JavaScript disabled in the same engine, and requires the hydrated page to keep that mode and content with no hydration diagnostic, console error, page error or failed required asset. It then opens the Dialog by keyboard and compares the extracted Button and the root, control, status and portal tokens and paint with the draft, before Escape returns focus. `--fault src-extraction` (next-src), `--fault hydration-mismatch` and `--fault portal-theme` each build and fail their cells in every engine.

`--layout vite --exercise elements` runs the element lifecycle on its own light-DOM fixture: a vanilla Vite TypeScript scaffold with no React, no setup item and no `components.json`. Every element item installs from the registry with `tokens-css`, the page loads each vendored file as its install docs print, and the generated CSS theme follows the tokens. That gives 6 cells, IDs `vite/elements/<engine>/lifecycle-<mode>`. Each cell checks that every catalogue tag is defined and upgraded, including one created after definition. It moves `ult-tabs` and `ult-button` to check a reconnect renders once. Attribute updates on `ult-tabs`, a tab and `ult-button` must reach the rendered controls' state and paint, then revert. `ult-tabs` must follow arrows past a disabled tab, manual activation, Home and End, and its selected, muted, indicator, border and focus-ring colors must come from the installed draft in the cell's mode. The element run packs no CLI, so its report carries no tarball digest.

Both exercises reuse the bundles runner: one build per run, two cells at a time per engine, the same snapshot, trace and identity evidence, and a per-bundle deadline (`CELL_DEADLINES_MS`). Each snapshot records the cell's `durationMs`. The deadlines are about five times each bundle's slowest cell in the first complete CI run, [#804](https://github.com/frankieramirez/ultima/pull/804), and never under 30 seconds. That run's slowest cells were theme and CSS 11.5 s, hydration 9.1 s, element lifecycle 6.4 s, overlay and keyboard 5.7 s and form 2.8 s, which gives 60, 45, 30, 30 and 30 seconds. The verifier registers them as `consumer-bundles-next-app`, `consumer-bundles-next-src` and `consumer-elements`.

### Matrix and weekly run

`matrixCases()` in `scripts/consumer-report.ts` lists every registered cross-engine cell: the Vite bundles, the Next hydration cells and the element cells. `scripts/consumer-matrix.ts <reports> --summary <file>` reads every retained bundles and elements report, and requires each to be valid and every report to name one source head. Outside a pull request, the executed cell IDs must equal `matrixCases()` exactly. A failed cell, an invalid report, or a failed or cancelled job in the run fails the matrix. A missing or duplicated cell, or a second revision, leaves it incomplete. The summary records each bundle's cell count, slowest cell and total cell time.

The installed-consumer workflow runs every cell weekly (Mondays 06:17 UTC) and on manual dispatch, as on a push to `main`. Its `matrix` job runs the summary after every other job. When a scheduled run fails, `consumer-matrix.ts --file-issue` opens the issue titled "Weekly installed-consumer matrix failed", or comments on it while it stays open.

### External-project mode

`node --experimental-strip-types scripts/consumer-proof.ts --external <dir> [--output <dir>]` runs the [first-screen exercise](adoption-delivery.md#first-screen-exercise)'s production assertions against a project the runner did not scaffold. It reads the layout from the project's `package.json` and `src/app` folder, decodes the installed `ultima-theme.json`, runs `npm run build` and serves the production output: `dist` over loopback for Vite, `next start` for Next. Each of the system and explicit dark and light cases checks every resolved token and `color-scheme` on the document root and the open popup, horizontal overflow at 375, 768 and 1280 pixels, the named error on a required field after a submit, keyboard Enter on the first `aria-haspopup` or combobox control, a popup rendered outside the trigger's tree with focus inside it, Escape and focus return, axe with the popup closed and open, and no console error, hydration warning, page error or failed required asset. It finds elements by role, ARIA state and semantic token, never by a scene test ID. `report.json` records the source revision and manifest, the draft digest and fingerprint, framework and browser versions, and each case's values, axe report, browser log and screenshot. Exit 0 is a pass, 1 a failed case, 2 an incomplete run such as a failed build or a missing draft.

## Delivery paths

Use the same draft and scene for four delivery checks:

1. **Generated CSS, primary path.** Install the local theme registry item, retain its draft JSON, import `ultima-theme.css` after the base StyleX output, and exercise system preference plus explicit dark and light `data-theme` on the document root. Assert the installed files and imports, then run the browser obligations below. This is the primary Vite and both Next-layout path.
2. **Compiled StyleX, subtree path.** Put the generated module in a compiler-included consumer path, apply every complete group theme and `colorScheme` on a subtree, and mount its portal container inside that subtree. Assert that its compiled values match the draft and that the portal inherits this subtree instead of the document theme. Test the consumer alias and compiler setup in Vite and both Next layouts. A missing extraction or partial group application fails.
3. **Registry installation.** Install the downloaded self-contained theme item with shadcn in a fresh project, verify both emitted theme files and the draft fingerprint, and compare its computed values with the direct generated CSS result. Do not copy files into the fixture as a substitute for this check. The primary path can satisfy this obligation when it truly uses that install route; do not duplicate its browser matrix.
4. **Packed CLI.** Install the `pnpm pack` tarball into the disposable project from its own dependencies. Run `ultima-design doctor` and `check` against each layout and require successful, complete reports. This establishes consumer setup and source rules alongside the browser result; a CLI pass alone is not rendered proof.

Keep the existing Studio preview/CSS/StyleX parity corpus for stock, shuffled, overridden and acknowledged failing user drafts. The integrated proof uses a shipped passing draft and tests actual installation, extracted production CSS, alias resolution, cascade, portals and hydration. Preset revisions also follow [the complete preset release bar](theme-studio.md#release-bar-and-consumer-guidance): every shipped preset must pass its own two-mode pairing and installed-consumer parity checks. Reuse this fixture and its assertions rather than multiplying application scaffolds for each preset.

## StyleX lint proof

The [consumer lint contract](consumer-lint.md), decided on [Decide the StyleX linting contract for consumer projects](https://github.com/frankieramirez/ultima/issues/730), adds official StyleX lint to the same installed Vite and Next root/src fixtures. Run the project's local lint command once per immutable layout build before production compilation, alongside packed CLI doctor/check. Retain effective-config probes, exact plugin/ESLint/parser versions, file coverage and positive/negative diagnostics. Prove absent-config setup, preservation of existing rules/ignores and offline execution. Static doctor detection is not an executed lint pass. Reuse this result across browser/mode cells; the 54-cell browser matrix and rendered obligations stay unchanged. The runner's `lint` exercise (`scripts/consumer-lint.ts`, [#756](https://github.com/frankieramirez/ultima/issues/756)) implements it; [consumer-lint.md](consumer-lint.md#verification-and-delivery) lists its cases.

## Browser pass conditions

Run the shared scene in production browsers, using the 54-cell cross-engine matrix and its framework/element split settled on [the browser-support decision](https://github.com/frankieramirez/ultima/issues/618). This fixture supplies the Vite and Next cells; the element lifecycle cells keep their own light-DOM fixture. A cell passes only when all applicable assertions below pass in both dark and light. The system-preference check additionally changes the emulated preference without an explicit attribute, then forces each explicit mode to show that it overrides the preference.

- **Real paint and parity:** the app root, accent control, status content and open portal have nontransparent or otherwise observable computed paint where their contract calls for it. Compare representative computed semantic variables, `color-scheme`, background, text, border and focus styles to the resolved draft and across CSS/StyleX/registry outputs. Verify that the non-stock sample actually differs from Neutral/Ultima on chosen roles. Compare shadows and font-stack strings where present; do not mistake an unloaded preferred face for a token mismatch.
- **Navigation and form:** keyboard navigation reaches the destination and current state updates. Form labels and errors have accessible names; required validation, selection, submit and reset produce the expected visible state and serialized values. Assert the installed data content's expected row and empty-state transition. Exercise both pointer and keyboard activation on at least one control.
- **Overlay and focus:** opening the portal exposes the right role and name, places focus inside it, keeps its computed theme values and `color-scheme` equal to its intended root or subtree, supports keyboard action and Escape, and restores focus to the trigger. Confirm the popup is actually portalled and that its open state is included in accessibility checks.
- **Hydration and motion:** compare the server HTML's initial mode and visible content with the hydrated Next page. Require no hydration warning, React error, uncaught page error, failed required asset, or missing StyleX extraction. Switch modes after hydration and assert values change without stale portal styling. With reduced motion enabled, assert the export's fixed fast/base/slow collapse and loop value through computed styles while interaction remains usable.
- **Accessibility:** run axe on the rendered scene with the overlay closed and open in both modes. The token pairing gate remains separate; a passing axe run does not replace computed theme, keyboard or hydration assertions.

Every assertion must target a stable role, accessible name, test ID for a value probe, or a known semantic token. Do not bless a screenshot as the sole oracle. On failure, retain the fixture directory, build and server logs, browser console/page errors, failed requests, accessibility report, screenshot and a JSON snapshot of expected versus computed values with mode, engine, layout and delivery path. Include the exact failing command so a developer can reproduce one cell. A missing or incomplete report is a failure, not a pass.

## Gates and cost

The [adoption delivery plan](adoption-delivery.md) sequences this runner (slice S2) and its 54-cell expansion (S8), and reuses it for the first-screen exercise.

Relevant PRs run the affected installed-consumer cases and delivery paths when setup, tokens, theme resolution/export, registry metadata, components used by the scene, StyleX configuration, CLI or the verifier changes. Shared resolver, runner, browser configuration or dependency changes run the full shared matrix. Unknown dependency impact expands to the full matrix rather than silently skipping a case. Keep the existing full-catalogue smoke install trigger and checks. `scripts/consumer-select.ts` implements this selection in `.github/workflows/consumer-proof.yml`: it plans `pnpm verify changed` against the pull request's base and turns the selected `consumer-proof`, `consumer-mode`, `consumer-copy`, `consumer-lint`, `consumer-bundles` and `consumer-elements` checks into the job matrices, so prose selects no cell, a token, theme export, StyleX configuration, runner, verifier or dependency change selects every cell, and an unknown base or unresolved dependency edge broadens to the release plan. A scene component, copy-bundle item or setup item selects the layouts that install it, an element item or its React counterpart selects the element cells, any React component or block selects the lint cells, and a CLI change selects the packed-CLI and lint cells. A push to `main` runs every cell. The full set's warm CI time on [#788](https://github.com/frankieramirez/ultima/pull/788), with the pnpm store cached, was 5 minutes 21 seconds of wall-clock time: 16 seconds to select, about 2 minutes per CSS, subtree, CLI or theme-mode cell, and 4 to 5 minutes per registry cell, about 38 runner-minutes in all. That is within the 15-minute additional budget. The measurement predates the copy-bundle and lint jobs, which run in parallel with the others. On [#804](https://github.com/frankieramirez/ultima/pull/804), with every cell selected, the 36 registered cross-engine cells took 2 minutes 34 seconds of warm wall-clock time across their four parallel jobs: Vite bundles 2:34, next-app 2:13, next-src 2:23 and elements 1:42, each including install, scaffold and build. Select and the matrix job add 30 seconds, about 3 minutes in all, within the 15-minute budget. The whole workflow took 5 minutes 35 seconds. Use one scaffold per layout and reuse it across mode/browser assertions; cache immutable package downloads, not installed source or generated output being tested. Report warm-CI time and tune selection against the browser-support decision's initial 15-minute additional budget, without dropping a required assertion to meet it.

A release recommendation requires the full shared 54-cell browser matrix, all four delivery obligations, the existing smoke install, Studio pairing/parity gates and `pnpm verify release` green on the same source revision. Record the report IDs and artifact hashes. A failed preset revision blocks a recommendation for that preset and any release that includes it. Weekly runs and dependency/browser upgrades refresh the complete evidence; stale reports do not prove a changed build.

The local loopback fixture proves a reproducible installed application. The separate live-domain stranger-path check already required by [the public launch effort](https://github.com/frankieramirez/ultima/issues/587) must fetch the public registry and documentation without repository or local-build shortcuts and verify the promoted artifact and theme in a fresh consumer. Record the public URL, fetched artifact hashes, install commands and browser result. It gates a public production claim and promotion, not ordinary PRs. A green local report cannot stand in for it. This plan neither publishes the repository nor authorizes a site or package release.
