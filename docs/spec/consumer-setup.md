# Consumer project bootstrap

Decided on [Decide the supported project bootstrap experience](https://github.com/frankieramirez/ultima/issues/726), under [Map: Make Ultima a plug-and-play StyleX design system](https://github.com/frankieramirez/ultima/issues/725). Status: accepted for implementation. The new-project paths for Vite ([#765](https://github.com/frankieramirez/ultima/issues/765)) and Next root and `src` ([#766](https://github.com/frankieramirez/ultima/issues/766)), the existing-project path for Vite and both Next layouts ([#767](https://github.com/frankieramirez/ultima/issues/767)), and its recovery journal, resume and rollback ([#768](https://github.com/frankieramirez/ultima/issues/768)) are implemented; [As built](#as-built) records their exact shape. Harness delegation is still future behavior, and the current [install walkthrough](../../apps/docs/src/content/install.mdx) remains their usable entry. [Ultima's principles](ultima.md#principles), [Theme adoption](ultima.md#theme-adoption) and [ADR 0005](../adr/0005-hosted-agent-guidance.md) set the ownership boundaries.

## Entry point and command journey

Make `npx ultima-design@latest init` the primary guided entry. For a new directory it invokes a pinned official framework scaffold, installs Ultima through shadcn, and completes supported setup edits. For an existing directory it detects the application and proposes bounded edits. Ultima maintains integration recipes and a small preview, rather than separate starter repositories. The framework owns its scaffold; installed source and application edits belong to the consumer.

Before writing, interactive `init` shows the target, layout, exact dependencies, file diffs, subprocess commands and manual steps, then asks to apply. Cancellation leaves the project unchanged. `--plan --json` emits a versioned plan without writing project files, installing packages or executing configuration. `--apply <plan.json>` applies an inspected plan without another prompt. Noninteractive calls without either mode refuse to write. Plan operations are typed recipe data, never arbitrary shell commands.

New-project examples, once implemented:

```sh
npx ultima-design@latest init my-app --framework vite --package-manager pnpm --harness codex
npx ultima-design@latest init my-next-app --framework next --layout src --package-manager npm
```

The first previews a Vite React TypeScript application, setup, preview and pinned CLI dependency, plus Codex's managed skill and hook. The second creates Next App Router under `src/app`. Next defaults to root `app` for a new project when layout is omitted; Vite uses `src`. Framework selection is required for an empty target. Both recipes disable Tailwind and optional React Compiler integrations. The pinned Next scaffold recipe disables git initialization and optional agent-document/feedback generation. `init` creates no commit or repository. Verify those options against the pinned scaffold; do not rely on remembered prompts or upstream defaults.

Existing-project example:

```sh
npx ultima-design@latest init . --plan --json > /tmp/ultima-init-plan.json
npx ultima-design@latest init --apply /tmp/ultima-init-plan.json
```

The plan records the canonical application root, CLI and recipe identity, input hashes, registry payload hashes, manager/version, harness selection and output inventory. Apply rechecks these inputs before edits. Stale files or changed registry payloads require replanning. A plan cannot override an existing framework/layout mismatch; `--apply` accepts only the plan path, so other options cannot change reviewed operations. Network failure or an unknown plan version returns an incomplete result.

## Supported layouts and compatibility

| Target | Initial automated contract |
| --- | --- |
| Vite React TypeScript | Root `package.json`, `vite.config.ts`, `index.html`, `src/main.tsx`. `@/*` resolves to `./src/*` in root/application tsconfigs. Fresh aliases install UI under `src/components/ui` and shared source under `src/lib`. |
| Next App Router TypeScript, root | Root configuration, `app/layout.tsx`, `@/*` resolving inside the root. Fresh UI/shared paths are `components/ui` and `lib`; marker CSS lives under `app`. |
| Next App Router TypeScript, src | Root configuration, `src/app/layout.tsx`, `@/*` resolving to `./src/*`. Fresh UI/shared paths are `src/components/ui` and `src/lib`; marker CSS lives under `src/app`. Leave no unused root `app` directory. |

Require one unambiguous application and active layout. Follow tsconfig inheritance when resolving aliases. Preserve existing compatible `components.json` aliases that resolve inside the application and satisfy doctor/check. Fresh files use the defaults above. Conflicting `@/` targets, incompatible style/RSC/transform settings, dual active Next layouts or an incompatible registry installation block automatic apply. Keep unrelated namespaces and configuration keys.

Initially automate npm and pnpm with `node_modules`. Detect the lockfile and `packageManager` field, preserving both. Multiple lockfiles or conflicting manager declarations require a resolved choice before planning. New projects use an explicit manager flag, otherwise an unambiguous enclosing preference or npm. Record and use the exact manager version. Do not convert an existing lockfile or mutate an enclosing workspace. Yarn, Bun, PnP, workspace-wide setup, Next Pages Router, JavaScript-only apps and custom source roots follow manual setup until separately verified.

Each CLI release bundles exact tested scaffold/framework/React/StyleX/primitive/manager combinations, their Node engine intersection and recognized configuration shapes. A new project selects a recipe instead of independently resolving every dependency to latest. Existing dependencies must meet declared peers and a tested recipe, including matching StyleX runtime/compiler versions. If compatibility requires upgrading existing framework, React or StyleX dependencies, refuse automatic apply and print the manual upgrade. Above-tested versions may remain advisory in `doctor` while blocking automatic initialization; unknown versions are incomplete. Check resolved versions after installation against the approved recipe.

Setup/component descriptors own dependencies. Vite uses the StyleX runtime, unplugin and `unplugin`; Next uses the runtime, Babel/PostCSS plugins and TypeScript. Components install their primitive and shared registry dependencies transitively. `init` adds a pinned `ultima-design` dev dependency using the selected manager. Components, tokens and shared source still come through shadcn; no additional `@ultima/*` npm package or second installer is introduced.

## File and edit contract

| Files | New project | Existing project |
| --- | --- | --- |
| `package.json`, selected lockfile | Scaffold dependencies, approved Ultima dependencies and pinned CLI. | Add approved missing dependencies, preserving scripts and unrelated metadata. The selected manager owns lockfile updates. |
| `components.json`, `ultima.vite.ts`, Next Babel/PostCSS config, marker CSS | Install registry setup assets and adapt the selected layout. | Create absent assets; preserve equivalent files. Propose syntax-aware additions to recognized shapes, preserving other plugins/options. Conflicting or computed shapes require manual repair. |
| Root/application tsconfigs, `vite.config.ts` | Complete aliases; put `ultimaStylex()` before React. | Add only missing compatible entries, retaining comments and existing options. Never execute configuration to inspect it. |
| CSS entry, resets, Next layout | Wire the marker once and layer the scaffold reset. | Show import/reset diffs. Move only recognized reset rules into `@layer reset`, preserving order and application/theme rules. Unknown CSS requires manual repair. Keep providers, metadata, mode attributes and font loading. |
| Registry components/shared source | Install Button, Card and Dialog and their transitive dependencies through shadcn. | Install only missing items. Preserve existing source; edited, unstamped or incompatible collisions require consumer review outside automatic apply. Never pass blanket overwrite. |
| Preview and route | Replace only the recognized scaffold example with the preview on `/`. | Next adds an unused `/ultima-preview` route. Vite adds `src/ultima-preview.tsx` and prints the exact import/render step for the consumer's application/router. Preserve existing pages and routing; collisions block creation. |
| Theme artifacts, root documents | Use accepted Neutral/Tight base after its coupled rollout. Preserve the framework's README. | Preserve theme CSS, JSON draft, `DESIGN.md`, `AGENTS.md`, `CLAUDE.md`, README and rules files. Report theme/import state and unresolved brand/cascade work; never substitute Neutral automatically. |
| Agent files | Delegate detected or explicitly selected harnesses to existing `install`. | Use the same reviewed delegation, retaining foreign hooks and external-installer skills. Edited managed skills and invalid hook JSON remain conflicts. |

This command is a separate bounded-write exception in ADR 0005. `install` keeps its existing managed-skill/hook write set. `init` neither writes nor merges root guidance documents. Product-theme discovery, design-document handling, full-screen recipes, mode/portal packaging and lint policy remain with the other map questions. Report those requirements without settling them here.

## Conflicts, idempotence and recovery

Validate the complete inventory before application writes. Targets must stay inside the chosen application; refuse escaping symlinks and edits to inherited config outside it. Existing uncommitted changes may participate only through inspected hashes/diffs. Execute subprocesses with structured arguments and a fixed root.

For a new project, apply in private staging, verify the scaffold matches its recipe, then publish into the absent destination after setup checks and build pass. Refuse an existing destination, including a race during apply. On failure retain the staging path and logs while leaving the requested destination absent. A separately scaffolded empty app uses the existing-project path.

For an existing app, save original bytes and modes for the write inventory in a private recovery directory first. Journal operations, before/after hashes and subprocess outcomes. Inspect and pin registry payloads and transitive destinations before shadcn writes; reject unexpected targets or payload changes. Stop subsequent operations on failure/interruption. A rerun reconciles the journal with actual files, proposing only missing work and preserving intervening consumer edits.

`init --rollback <run-id>` restores originals or removes created files only when the current hashes match this run's recorded outputs. Otherwise name the consumer edit and leave it for manual recovery. Retain failed subprocess logs. Package-manager effects cannot be an atomic file transaction: restore package/lockfile bytes where safe and print the exact reinstall command. Do not promise to restore arbitrary lifecycle-script effects or delete shared package caches. Successful reruns create no duplicate imports, plugins, dependencies, routes or hooks, and never replace edited installed source.

## Finish state and checks

The small preview contains a heading, a Card surface, a Button that changes visible state, and a named Dialog with focus restoration. Its arrangement uses StyleX/semantic tokens and fits a narrow viewport. It imports installed consumer source. Next retains a server page with the interactive preview behind a client boundary. New applications use system mode with the accepted dark fallback and documented explicit dark/light activation. Font loading remains consumer-owned. A persisted mode switch or custom theme is separate work. Completing the coupled Neutral/Tight base rollout is a prerequisite for recommending this entry point.

Run the pinned local CLI's `doctor` and `check`, the recipe's typecheck and production build; retain each result. The generated new project must complete all of them. Existing application failures stay visible and prevent a completion claim. Result conventions remain: 0 for completed required setup/checks, 1 for failed checks or conflicts, 2 for invalid invocation, 3 for an incomplete run. A manual mounting/theme step or an unexecuted required check keeps the result incomplete, even when installation succeeded.

Print created/edited/preserved files, resolved versions, recovery path, check results, and exact dev/production commands and preview URL. State whether the screen was mounted and whether browser checks ran. Every remaining manual step names its file, copyable edit/command and verification. After the printed Vite mount step, rerun `init` to verify setup and build. Harness selection uses `install`'s detection and repeatable override. With none detected, report skipped agent setup and the exact pinned install command; this does not block the application. Harness trust prompts stay the consumer's next action.

Current managed hooks resolve the Git repository root before running the CLI. Delegate hook installation only when that root equals the selected application root. A fresh project without Git, or an application nested in another repository, skips hook setup and reports it explicitly. For a standalone fresh app, print `git init` as an optional consumer action followed by the selected manager's command to run the pinned CLI's `install --harness <name>`; never initialize Git on the consumer's behalf. Nested applications need a manual hook integration and cannot be reported as agent-ready. The new-project Codex example therefore records the harness choice but defers its hooks until this prerequisite is met. This keeps the existing hook contract unchanged.

Ordinary initialization does not install a browser or derive rendered proof from static/build checks. Supported recipes require retained production-browser acceptance before publication. Reuse [Rendered consumer proof](consumer-proof.md) and [Consumer support](consumer-support.md), their shared 54-cell matrix and source/registry/tarball identity. The preview smoke supplements those fixtures, preserving the complete form/navigation/custom-theme scene. The six framework/layout/manager install paths below are bootstrap coverage, not six additional copies of the browser matrix. [Decide the adoption delivery order and first-screen acceptance test](https://github.com/frankieramirez/ultima/issues/731) owns ordering and the public-guidance exercise.

## Implementation acceptance scenarios

- New Vite, Next root and Next src apps reach the preview with npm and pnpm. Run all six paths using the packed CLI outside this workspace, retain exact lockfiles/versions and production artifacts, and verify interaction/paint in both modes using shared browser fixtures.
- Browser checks assert root/control/Dialog paint, responsive fit, Button update, keyboard focus and Escape/restoration. Next hydrates without diagnostics. Seed missing CSS, wrong src extraction, unlayered reset and missing transitive source; each must fail observably.
- Existing Vite preserves its router/page and prints the preview-mount step; both Next layouts add only the isolated route. Providers, metadata, fonts, mode/theme artifacts, root documents and foreign hooks survive except for inspected setup edits.
- Compatible foreign plugins/registry entries survive apply. A rerun writes nothing, and consumer edits to installed source or preview survive. A framework-version change triggers replanning rather than migration.
- Conflicting aliases/layouts, computed configs, unsupported recipes, multiple lockfiles and escaping paths fail before application writes. Manual repair followed by a fresh plan can proceed.
- Cancellation/plan leave the project unchanged. Stale, tampered, unknown-version or changed-registry plans fail before writes. Noninteractive ambiguity and invalid invocation return their declared results.
- Interrupt scaffolding, package installation, registry installation and config edits separately. Verify staging/recovery behavior, resume without duplicates and rollback matching outputs only. Intervening consumer changes remain intact with a named recovery action.
- Cover detected/explicit/no harness, matching Git root, fresh app without Git, nested application root, edited managed skill, external-installer skill and invalid hook JSON. Preserve existing `install`/`uninstall` scope tests. Reports distinguish application readiness, deferred agent setup, static checks, build, browser and incomplete/manual outcomes.

## As built

[#765](https://github.com/frankieramirez/ultima/issues/765) implements the walking skeleton: `init <directory> --framework vite` for a new directory, with `--package-manager npm|pnpm` (npm when omitted). [#766](https://github.com/frankieramirez/ultima/issues/766) adds `--framework next` with `--layout root|src`, root when omitted. Vite takes only `src`.

- **Recipe data.** `packages/cli/src/recipe.ts` holds the `vite-react-ts` recipe: `create-vite@9.2.1` with the `react-ts` template, `shadcn@4.21.4`, exact versions for every dependency, the sha256 of each file the pinned scaffold writes, and the files the recipe writes. StyleX and Base UI pins equal the versions the workspace tests. `init` builds each subprocess from these fields as structured arguments: `npx --yes` or `pnpm dlx` for the pinned scaffold and shadcn, the selected manager for install, `exec` and `run`.
- **Operations.** Scaffold, verify the scaffold's inventory and hashes, pin `package.json` and add the `@/*` alias to `tsconfig.json` and `tsconfig.app.json`, install, add `setup-vite`, add Button, Card and Dialog, put `ultimaStylex()` before React in `vite.config.ts`, replace `src/index.css` with a layered reset and token-painted root, replace the scaffold example in `src/App.tsx` with the preview, remove the example's own assets, verify every installed version, then run `ultima doctor`, `ultima check`, `tsc -b` and the build. A write or removal first checks that the file still holds the bytes the plan expected.
- **Next recipes.** `next-app-router-ts-root` and `next-app-router-ts-src` run `create-next-app@16.4.0` with every choice explicit, so preferences it saved on the machine cannot change the scaffold: TypeScript, App Router, `--src-dir` or `--no-src-dir`, the `@/*` alias, and no Tailwind, React Compiler, ESLint, Biome, Rspack, AGENTS.md, agent feedback, git repository or install. Cache Components stays on, as the scaffold's default. `--use-npm` or `--use-pnpm` follows the manager; with pnpm the scaffold also writes `pnpm-workspace.yaml` and records `packageManager`, and the recipe hashes both. The verified inventory has no `.git`, `AGENTS.md`, `CLAUDE.md` or Tailwind file. Next, React, StyleX and Base UI pins match the Vite recipe and the workspace: `next` 16.4.0, `react` 19.3.0, `@stylexjs/stylex`, `@stylexjs/babel-plugin` and `@stylexjs/postcss-plugin` 0.19.0, `@base-ui/react` 1.8.0, `typescript` 5.9.3. Each recipe records the Node engine intersection of its pinned packages and the CLI's own `>=22`, and planning refuses an older Node (exit 1): `22.12.0` for Vite, where create-vite, Vite, its React plugin and oxlint take `^20.19.0 || >=22.12.0`, and `22.0.0` for Next, where create-next-app and Next take `>=20.9.0` and shadcn `>=20.18.1`.
- **Next operations.** Scaffold, verify, pin `package.json`, install, add `setup-next`, add Button, Card and Dialog, then wire the layout's app directory: import `./ultima.css` after `./globals.css` in `layout.tsx`, replace `globals.css` with the layered reset and token-painted root, and replace the example page with a server `page.tsx` that renders the interactive preview from a `'use client'` `setup-check.tsx`. Metadata and the scaffold's font loading stay. For `src`, the setup item's `app/ultima.css` moves to `src/app/ultima.css`, only while it holds the pinned payload's bytes, and the emptied root `app` goes with it; `components.json` names `src/app/globals.css`. The example's stylesheet and `public` images are removed. `next typegen` writes the route types before `ultima doctor`, `ultima check`, `tsc --noEmit` and `next build`. Next's build output records the staging directory's absolute paths, and a build in the published directory then fails to find staging's `babel.config.js`, so apply removes `.next` before publishing; the consumer's first `next build` starts clean.
- **Plan.** `--plan --json` prints a schema-version-1 plan: CLI version and commit, recipe identity and hash, the request, the manager and its version, Node's version, the destination's absence, the hash of each registry payload with its transitive `@ultima` dependencies, the dependencies, every operation with its file content and diff, and the manual steps. `planHash` covers the rest. `--plan` alone prints the same plan for reading. A terminal run prints it and asks; a cancel exits 3 and writes nothing. Outside a terminal, `init` refuses without `--plan` or `--apply` (exit 2).
- **Apply.** `--apply <plan.json>` takes no other option. An unknown kind or version is incomplete (exit 3). An edited plan fails its hash (exit 1). Apply then plans again from the recorded request and requires the identical hash, so a changed CLI, recipe, manager version, Node version, payload or destination is stale (exit 1). Nothing is written before these checks.
- **Staging and publication.** Apply works in a private `.ultima-init-<name>-*` directory beside the destination. It claims the destination with a single `mkdir` only after every check passes, then moves the application in. A destination that appeared during apply is left untouched. On any failure the destination stays absent and the staging directory keeps the application, `plan.json`, `result.json` and each subprocess log. On success the logs move to `node_modules/.ultima-init/<run-id>/` and the staging directory is removed.
- **Exits.** 0 when every operation and check completed; 1 for a failed check, a conflict, a stale or edited plan, or an existing destination; 2 for an invalid invocation; 3 for a cancel, an unreachable registry, a failed scaffold, install or registry subprocess, or an unknown plan version.
- **Candidate builds.** `--registry <url>/r/{name}.json` points the plan and the installed `components.json` at another registry. `--cli-tarball <path.tgz>` pins that packed CLI as the dev dependency and records its hash. Both are recorded in the plan.
- **Refusals.** An existing destination, even an empty one, a destination inside a pnpm or npm workspace, a parent directory that does not exist, and a directory name that is not a lowercase package name.
- **Installed-consumer case.** `node --experimental-strip-types scripts/consumer-init.ts [--case vite|next-root|next-src]... [--manager npm|pnpm]... [--no-faults]` builds the registry, packs and installs the CLI outside the workspace, plans and applies each layout with each manager, six paths by default, confirms that applying the same plan again is refused, rebuilds each published app where it now lives, and keeps each lockfile and production build beside the report. Chromium then loads each production build, `vite build` output or `next start`, in system dark and light. It checks root, Button and Dialog paint against the Neutral base tokens and `color-scheme`, that the Button keeps its token padding, that the page fits at 375px, that the Button updates, which on Next also proves hydration, that the Dialog opens from the keyboard by its name, that Escape returns focus, and that the console has no error, hydration warning or failed required asset. In the first manager's app of each layout it then seeds faults one at a time, rebuilds, and requires each to fail: the marker or CSS entry import removed, an unlayered `* { padding: 0; margin: 0 }` reset, the transitive `lib/component.ts` deleted, and on Next a PostCSS `include` that misses the layout's source. The report goes to `.scratch/consumer-proof/init-<time>/`. Chromium reports a light preference when the system states none, so the dark fallback has no browser case.

### Existing projects

[#767](https://github.com/frankieramirez/ultima/issues/767) implements `init <directory>` for a directory that holds a `package.json`, with the same `--plan [--json]`, terminal prompt and `--apply <plan.json>` journey. `--framework vite|next` and `--package-manager npm|pnpm` are optional there and may only confirm what detection finds. The code is `packages/cli/src/detect.ts` (the detection result), `edits.ts` (the syntax-aware edits) and `existing.ts` (plan, apply and report).

- **Detection.** One application at the canonical root (symlinks resolved). Next when `next` is declared, otherwise Vite when `vite` is; `react`, `react-dom`, `typescript` and `tsconfig.json` are required. Vite needs a single `vite.config.ts`, `index.html`, `src/main.tsx` and a React plugin. Next needs exactly one of `app/layout.tsx` and `src/app/layout.tsx`. The manager comes from the one lockfile, or the `packageManager` field, or the flag, or npm; lockfiles that disagree, a field that disagrees with the lockfile, a flag that disagrees with either, Yarn, Bun, Plug'n'Play, and a workspace root or member are conflicts.
- **Versions.** Every declared tested package must resolve from `node_modules`, or planning is incomplete. Each has a tested line: React and React DOM 19 from 19.0.0, Vite 8 from 8.0.0, Next 16 from 16.0.0, TypeScript 5.0.0 to below 7, Base UI 1 from 1.8.0, StyleX 0.19. A version below its line names the upgrade; one above it blocks automatic setup. Every installed `@stylexjs` package must resolve to one version.
- **Edits.** Missing dependencies only, at the new-project recipe's pins, inserted in place in `package.json`; a StyleX package joins the StyleX version already installed. `ultima-design` is added at this CLI's version when absent. `@/*` is added to `tsconfig.json`, and to `tsconfig.app.json` for Vite, following `extends`: an inherited `paths` inside the application is edited where it is declared, one outside it is a conflict, and a `@/*` that does not point at the layout's source root (`src`, or the root for Next `app`) is a conflict. `components.json` is created from the setup item, or kept when its style is `base-ultima`, `rsc` matches the framework, `tsx` is true and `ui`/`lib` are `@/` aliases; it gains only a missing `@ultima` registry. The other setup files are created when absent and kept when equal, or, for Babel, PostCSS and the marker stylesheet, when they already reference `@stylexjs/babel-plugin`, `@stylexjs/postcss-plugin` or `@stylex;`; anything else is a conflict. Vite gets `ultimaStylex()` first in a recognized `vite.config.ts`: a default export of an object, or of `defineConfig` called with one, whose `plugins` is an array literal calling the React plugin. A function, conditional or computed plugin list is a conflict. Next gets `import './ultima.css'` after the layout's last import, or before an `ultima-theme.css` import.
- **Resets.** Planning runs doctor's own layered-reset check from the entries. Each reset rule doctor flags in an application stylesheet is wrapped in `@layer reset { … }` where it stands, consecutive ones together, so application and theme rules keep their place. A selector list mixing resets and other selectors is split in place: the reset selectors move into the layer, the others keep the same declarations where they were. Resets in `index.html`, in a package stylesheet, behind a comment in the selector list, or in CSS that does not parse are conflicts.
- **Registry items.** Button, Card and Dialog are added through shadcn only when none of their files exist; an item whose files all exist is kept as it is, edited or not, and one that is partly there is a conflict. Every file the added items install, transitive ones included, must be absent or equal to the served source in its stamp's hash scheme; an edited, unstamped or foreign file there is a conflict, since shadcn would ask to overwrite it.
- **Preview.** Vite gets `src/ultima-preview.tsx`, and the plan prints the import and render step for `src/App.tsx`, with a route example when a router is declared. In an application `init` created, the starter screen (`src/App.tsx` for Vite, the app directory's `page.tsx` for Next) already is the mounted preview. Next gets `/ultima-preview`: a server `page.tsx` and a client `preview.tsx` in the active app directory. A file or route there that `init` did not write, including one under a route group or in `pages/`, is a conflict; one it did write is kept, edits included.
- **Preserved.** Root documents, theme artifacts and agent directories (`README.md`, `AGENTS.md`, `CLAUDE.md`, `DESIGN.md`, `ultima-theme.css`, `ultima-theme.json`, `.cursor/rules`, `.claude`, `.codex`, `.agents` and the like) are listed and never written. The entry files other than the edits above are kept. The theme state is reported: no exported theme, an exported theme the entry does not import, or one it imports. `init` never adds that import.
- **Plan and apply.** The plan records the request, the detection, the sha256 of every file planning read (null when absent), every resolved version, the payload hashes, the dependencies added and kept, the items added and kept with every file shadcn will create, each operation with its content and diff, the preserved files, the theme state, the preview and its mount step. Every conflict is found before anything is written; the plan fails with exit 1 and lists each with its file and repair, and with `--json` prints `status: "blocked"` and the list. Apply plans again from the recorded request and requires the identical hash, so any changed input is stale (exit 1). It then edits in place, checks each file's hash immediately before writing it, installs only when dependencies were added, and runs shadcn only for missing items. Each write goes through a sibling file and a rename, keeping the file's mode. A failed step stops the run; earlier steps stay applied, under the recovery record below.
- **Recovery.** `journal.ts` holds the record. A run that writes, installs or adds items creates `.ultima-init/<run-id>/` at the application root, mode 0700, beside a `.ultima-init/.gitignore` of `*` so the consumer's own ignore file is never edited. Before its first write it saves the bytes and mode of every path it may write (each write, `package.json` and the lockfile for install and shadcn, and every file shadcn will create) as `files/<sha256>`, with null for an absent path and the directories the run would create. `journal.json`, rewritten through a rename, records the run's status (`running`, `stopped`, `finished`, `rolled back`), each plan hash, the originals, the dependencies the run added, the pinned payload hashes and destinations, and each operation as `started`, then `done` or `failed`, with the sha256 of its paths before and after and a subprocess's exit and log. `outputs` keeps the sha256 each path held when the run last wrote it. The plan, result and subprocess logs sit beside it; a run that only checks keeps its logs in `node_modules/.ultima-init/<run-id>/` and has no journal. Immediately before shadcn runs, apply fetches every payload again and stops (exit 1) without running it when any hash differs from the plan's. A registry file whose target leaves the application, or lands on a file that is not that item's served source, is a conflict at planning.
- **Resume.** Planning reads the latest `running` or `stopped` journal and records it as `resume`. A dependency that run wrote to `package.json` and that is still declared as written but not installed is that run's pending install rather than an unknown version. When the run's last install or shadcn subprocess never finished, a tested package that resolved before the run and is now missing from `node_modules` is pending too, at the version it resolved to then. The plan installs what is pending and verifies it and every dependency the run added. A planned item whose present files are all destinations the run pinned and all equal the served source, with the rest missing, is added again rather than reported as partly installed. Everything the run finished drops out on its own, because each edit plans only what is missing: an interrupted install, shadcn run or config edit resumes without a duplicate import, plugin, dependency, route or reset layer, and a consumer edit made in between is planned against rather than replaced. Applying a resume plan continues the same run id and journal, numbering its plan, result and logs `2.`, `3.` and so on. A new project's interrupted scaffold keeps its staging and logs, and the destination stays absent, so the same plan applies again into a fresh staging directory.
- **Rollback.** `init [<app>] --rollback <run-id>` takes no other option. Each path in `outputs` that still holds that sha256 is restored to its original bytes and mode, or removed when the run created it, and the directories the run created are removed once empty. A path that holds neither its output nor its original is left and named, with the saved original to compare against or a note that the run created it. When `package.json` or the lockfile is restored or removed, it prints the reinstall: `npm ci` or `pnpm install --frozen-lockfile` when the original had a lockfile, otherwise `npm install` or `pnpm install`. Install-script effects and package caches are not undone. The journal becomes `rolled back`, so the next plan starts a new run. Exit 1 when a path was left, 3 when the reinstall is pending, 0 otherwise, and 2 for an unknown run id, which lists the runs recorded.
- **Checks and exits.** `ultima doctor`, `ultima check`, the typecheck (`tsc -b` for a Vite solution tsconfig, otherwise `tsc --noEmit`, after the build for Next) and the `build` script. 0 when every step and check completed and the preview is mounted; 3 while the Vite mount step is pending, without a build script, or when a subprocess failed; 1 for a failed check or a write whose file changed. After mounting, a rerun plans no writes, runs the checks and completes. A rerun on an applied project writes nothing.
- **Installed-consumer case.** `node --experimental-strip-types scripts/consumer-init-existing.ts [--layout vite|next-root|next-src]...` scaffolds each layout outside the workspace with its framework's generator, adds consumer content (a foreign Vite plugin, a Next provider around the layout's children, root documents), then plans and applies with the packed CLI against the candidate registry. It mounts the Vite preview from `src/main.tsx` as a consumer would, reruns `init` and requires a plan with no writes and no changed file, and checks that no file outside the plan's inventory changed apart from the lockfile and Next's own `tsconfig.json` and `next-env.d.ts`. Chromium loads each production build in system dark and light: the consumer's page, provider, font variables or foreign plugin still work, Button and Dialog paint equal the Neutral base tokens, the Button updates, the Dialog opens from the keyboard and Escape returns focus, and the console stays clean. The first layout named then runs a recovery case in a fresh copy: the apply is killed with its npm, as a closed terminal would, while the journal shows the install running; a fresh plan must resume that run from `install`, and its apply must leave the same files as the straight apply. A consumer then edits a file the run wrote, and `--rollback` must exit 1, name that file, and return every other file to its bytes before init, apart from what Next's build writes. The report goes to `.scratch/consumer-proof/init-existing-<time>/`.
