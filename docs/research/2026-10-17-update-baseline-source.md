# Where can `update` get the exact content a consumer installed?

Research for [#891](https://github.com/frankieramirez/ultima/issues/891), run on 2026-10-17 against this repository at `5c82f5b`.

## Findings

**Recommendation: read the public repository at the stamp's revision, for `c1` files only, and rebuild the staged text locally.** For each `diverged` file, `update` fetches the item's authored source from `raw.githubusercontent.com` at the 12-character revision. It applies the registry build's import rewrite, and the base-theme marker for `tokens`, then accepts the result as the base only when its `c1` hash equals the stamp's hash. Nothing new runs on the site or in CI. The repository is public, so this costs nothing to keep running. It does not reopen ADR 0003. `b1` files (element bundles and `tokens-css`) stay two-way. Their content is build output that is not in git. Element bundles are minified vendored artifacts whose edits ADR 0009 already forfeits. Only `diverged` files need a base, because a `behind` file is its own base (local equals installed).

I checked this against real served content:

- At the first stamped revision, `2a5a60a9` (#501), I built the registry from a `git archive` snapshot. All 60 stamped `c1` files rebuild byte for byte from `git show 2a5a60a9:<source>` using today's import rewrite, and all 60 hashes match.
- At `HEAD`, all 85 `c1` files (components, `lib`, `tokens`, blocks) rebuild byte for byte once the `tokens` marker line is appended. All 85 hashes match.
- `packages/cli/src/base-theme.ts` pins five hashes that the live registry served after #747. I rebuilt the four `c1` ones from git at `e2f9db14` (#747) and got `c1:1c6cb8e234999610`, `c1:dfa4ffe539e68f4e`, `c1:af35cf25640f91fa` and `c1:b034ecd8f51bede6`, which are exactly the pinned values. The fifth, `b1:a017b2da94928ac1` for `tokens.css`, also matched, but only after a workspace install and a tokens build at that revision.

I could not fetch `https://ultima.systems` from this session, because the egress proxy refuses the host. So no live `/r/*.json` was compared directly. The `base-theme.ts` hashes are the only values here that came from served output.

**ADR 0003.** Its versioning amendment set aside "versioned snapshot URLs, which the per-deploy rebuild of `apps/docs/public/` cannot keep", and the spec says there are "no versioned URLs". A per-revision snapshot on the site reopens that decision, and so does a hash-keyed store served from the site. The build would have to keep content across rebuilds, which is the fact the ADR relied on. A store kept in the repository is not a served URL, so it sidesteps the ADR's reason, but it is still new infrastructure. npm snapshots reopen the other 2026-09-22 amendment instead, which says components, the shared lib and elements "still reach a consumer only through the registry". The raw-source route reopens neither. It reads the source the registry was built from, and the stamp already names the revision for exactly this purpose.

**The spec is out of date on one point.** Versioning and drift says nothing serves the installed content because "the repository is private". The GitHub API now reports `"visibility": "public"` for `frankieramirez/ultima`. That premise of the open question no longer holds.

### What the raw-source route needs

- **A source path for each item.** The stamp names the item, and the catalogue entry names the staged path. The authored path follows from the staging plan: `packages/ui/src/<file>.tsx`, `packages/ui/src/lib/<file>.ts`, `packages/tokens/src/<file>.ts`, `packages/blocks/src/<id>/<file>.tsx`. If that layout moves, the CLI needs the old layout as well. The hash tells it when it guessed wrong.
- **The build's rules at that revision.** These are the `@ultima/*` to `@/registry/ultima/*` rewrite (unchanged since #527) and, from `c0385074` (#781) on, the `// @ultima-base neutral-tight` marker on `tokens` files. The marker is a comment, so the `c1` hash cannot tell whether it is there. Without it a three-way view shows a spurious one-line hunk.
- **The repository's coordinates.** `components.json` names `ultima.systems`, not GitHub. The CLI either hard-codes the repo or reads it from an added key such as `meta.ultima.source`. An added key does not need a format bump, because an older CLI does not misread it.
- **The installed rendering, not the staged text.** The base for a merge is the staged text after shadcn's transforms. `diff.ts`'s `renderAsInstalled` rewrites aliases and drops `"use client"` when `rsc` is false. shadcn also drops a file's leading comments, and `renderAsInstalled` does not model that. 4 of the 62 staged component, `lib` and `tokens` sources open with a comment, so a base built this way can carry a comment the consumer never received. The hash is unaffected, because `c1` neutralises both the staged `@/registry/ultima/*` specifiers and the consumer's aliases.

### Where each candidate breaks

- **Installed before stamps existed.** Stamps landed on 2026-09-22 in `2a5a60a9`. An older install is `unstamped` and carries no revision, so no candidate can find its base. Searching history for a revision whose hash equals the local file only works when the file is unedited, and then no merge is needed. `update` stays two-way for these files.
- **Revisions that never reached `main`.** The revision is `git rev-parse HEAD` at build time, cut to 12 characters. A PR preview deploy stamps a branch commit. With squash merges, that commit never lands on `main`, but it stays fetchable while it is a PR head: the head of #501 is not on `main` and still serves over raw. A commit lost to a force push, or a branch pushed without a PR, may not resolve. A build outside a git checkout stamps `local`, and so did my `git archive` builds: that revision resolves nowhere. A build from a dirty tree stamps `HEAD` while serving different content, and the hash check catches that. CI builds on `pull_request` check out an ephemeral merge commit, but those stamps only reach throwaway smoke consumers. In every case the hash check turns a wrong guess into "no base", never into a wrong merge.
- **`b1`: element bundles and `tokens-css`.** Their bytes are build output: `packages/tokens/dist/tokens.css` from the tokens generator, and the element bundles from esbuild with StyleX. Neither is in git, so raw source cannot give the base. A rebuild at the revision reproduces both. For a consumer that means a full workspace install, which is not practical. The element bundle is minified, so a three-way merge of it means nothing. `tokens.css` is the one `b1` file where a three-way view could help. If that is ever wanted, the cheapest source is a hash-keyed store of `b1` files that CI writes into the repository. It would start empty and cover only installs made after it begins.
- **Setup items.** `setup-vite` and `setup-next` come from `registry/static/` without a stamp or `meta.ultima`, by design. `design-md` carries no `meta` either. There is no revision to look up. Whether they landed stays `doctor`'s question.
