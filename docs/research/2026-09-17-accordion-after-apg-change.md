# What does Base UI 1.8's Accordion keep and drop after the APG roving-focus change, and what does its Panel add beyond Collapsible's?

## Findings

Base UI's Accordion is Collapsible run once per item under a shared value array. Its trigger is a native `<button>` with no keyboard handler of its own, its panel is `useCollapsiblePanel` with `role="region"` bolted on, and its `Header` is an `<h3>` whose level changes only through `render`. The roving-focus removal landed in v1.6.0, not 1.8.0; 1.8.0 is just the version installed here. `data-orientation` still renders on every part, and nothing reads it. `--accordion-panel-width` is a measured `scrollWidth` that no Base UI code reads either, kept for a consumer who animates width instead of height.

Answering the ticket's questions in order.

### 1. What the trigger does on the keyboard now

**Native button only.** `AccordionTrigger` in 1.8.0 has no `onKeyDown`. Its props are `aria-controls` (only while open), `aria-expanded`, `id`, and `onClick: handleTrigger`, merged with `getButtonProps` from `useButton({ disabled, focusableWhenDisabled: true, native: nativeButton })` (`accordion/trigger/AccordionTrigger.mjs`). `useButton` on a native `<button>` takes the early return in its `onKeyDown` (`!shouldClick || isNativeButton || ...`), so Enter and Space are the browser's own activation (`internals/use-button/useButton.mjs`, the `onKeyDown` branch). The only thing `useButton` adds is `focusableWhenDisabled`, which is why a disabled trigger renders `aria-disabled` and stays in the tab order rather than taking the `disabled` attribute.

`AccordionRoot` still wraps its element in `CompositeList` (for `index`) but no longer in `CompositeRoot`, and it destructures `loopFocus` and `orientation` only to discard the first and put the second into state (`accordion/root/AccordionRoot.mjs`). `AccordionRootContext` carries `disabled`, `handleValueChange`, `hiddenUntilFound`, `keepMounted`, `state`, `value` and nothing about focus.

**When it changed.** PR mui/base-ui#4965 "[accordion] Proposal: align Accordion keyboard navigation with APG", merged 2026-06-08, released in v1.6.0 (2026-06-18) as "Align keyboard navigation with APG (#4965)". Its diff removes `composite: true` from the trigger's `useButton`, the trigger's `tabIndex: 0` and whole `onKeyDown` (ArrowUp/Down/Left/Right, Home, End, `loopFocus` wrap, RTL flip through `direction`), the `accordionTriggerRefs` and `direction` from root context, and the `loopFocus = true` default. It adds the `@deprecated` JSDoc on `orientation` and `loopFocus` that reads "This prop no longer affects keyboard focus behavior." The changelog's v1.8.0 section has no Accordion entry; the deprecation is simply what 1.8.0 inherits. A companion docs PR, #4981, removed the same roving focus from the docs site's own accordion.

Consequence for the proof bar: Accordion's keyboard row is Collapsible's row, "Native button (Space, Enter). No arrow keys, no Escape", with one addition: Tab moves between triggers because each is a plain tabbable button. Item 4 covers it and item 7 has no candidate.

### 2. What the APG accordion pattern now requires

The change is w3c/aria-practices#3434, "Accordion Pattern: Remove optional arrow, home, and end keys", merged 2026-04-29, resolving issue #3406. The issue's complaint: once Up/Down arrows move focus between headers, "I can't scroll the page anymore to read the content of the accordion I've just opened." The PR touched only `content/patterns/accordion/accordion-pattern.html` and removed the four optional entries (Down Arrow, Up Arrow, Home, End) from Keyboard Interaction.

The current pattern's Keyboard Interaction is therefore three lines:

- Enter or Space: when focus is on the header of a collapsed panel, expands it; if the implementation allows it, collapses an expanded one.
- Tab: moves focus to the next focusable element; all focusable elements in the accordion are in the page tab sequence.
- Shift+Tab: the reverse.

Roles, states and properties, all of which Base UI's markup satisfies:

- The header title is in an element with role `button`.
- Each header button is wrapped in an element with role `heading` and an appropriate `aria-level`; native heading elements may be used. Base UI renders `<h3>`.
- The button is the only element inside the heading. A caret placed inside the button is fine; a sibling of the button is not.
- `aria-expanded` true/false on the button. `aria-controls` to the panel. Base UI emits `aria-controls` only while open; the APG example does the same.
- `aria-disabled="true"` when an expanded panel cannot be collapsed. Base UI's `aria-disabled` is the `focusableWhenDisabled` mapping of the `disabled` prop, a different meaning that happens to use the same attribute.
- Optionally, the panel has role `region` and `aria-labelledby` pointing at the button, and the pattern says to avoid that "in accordions that have more than approximately 6 panels". Base UI sets both unconditionally on every `Accordion.Panel` (`accordion/panel/AccordionPanel.mjs`, the `role: 'region'` and `'aria-labelledby': triggerId` props). There is no prop to turn it off; a consumer with a long accordion cannot follow the APG's six-panel advice without `render`. Ultima's docs should say the six-panel line is Base UI's default, not Ultima's choice.

### 3. Whether `data-orientation` still does anything

**It renders and nothing reads it.** `orientation` stays in `AccordionRootState`, `AccordionItemState` spreads root state, and `Header`, `Trigger` and `Panel` all take item state, so `getStateAttributesProps` emits `data-orientation="<value>"` on every part (`internals/getStateAttributesProps.mjs` writes `data-<key>` for any truthy string state without a custom mapping). No Base UI file under `accordion/` reads it after #4965, no CSS in the shipped docs selects on it, and `aria-orientation` was never set on the accordion (the v1.8.0 "Move `aria-orientation` to the role owners" entries are Autocomplete and Combobox). The shipped docs list `data-orientation` on Root and Panel only.

Rendered with `orientation="horizontal"` and `defaultValue={['a']}` through `react-dom/server` against the installed package, the attributes that actually appear are wider than the documented tables:

```
<div data-orientation="horizontal">                                                   Root
  <div data-orientation="horizontal" data-index="-1" data-open="">                     Item
    <h2 data-orientation="horizontal" data-index="-1" data-open="">                    Header (render={<h2 />})
      <button type="button" data-value="a" data-orientation="horizontal" data-index="-1"
              data-panel-open="" tabindex="0" aria-disabled="false"
              aria-controls="…" aria-expanded="true" id="…">A</button>                  Trigger
    </h2>
    <div data-orientation="horizontal" data-index="-1" data-open="" id="…"
         aria-labelledby="…" role="region"
         style="--accordion-panel-height:auto;--accordion-panel-width:auto;animation-name:none">
  <div data-orientation="horizontal" data-hidden="" data-index="-1" data-closed="">    closed Item
    <h3 data-orientation="horizontal" data-hidden="" data-index="-1" data-closed="">
      <button … data-value="a" data-orientation="horizontal" data-hidden="" data-index="-1" …>
```

Three undocumented leaks worth knowing before a build ticket writes selectors: `data-hidden` appears on Item, Header, Trigger and Panel of a closed item (from `AccordionItemState.hidden`, which no mapping suppresses); `data-closed` appears on Item and Header, not only Panel (the `collapsibleOpenStateMapping` is spread into `accordionStateAttributesMapping`, which Item, Header and Panel all use); and `data-value` appears on Trigger only, holding the root's open-value array stringified (`"a"`, or `"a,b"` under `multiple`), because `triggerOpenStateMapping` has no `value: () => null` while the Root, Item, Header and Panel mappings do. The `-1` index is the server value; `useCompositeListItem` guesses the index from render order on the client and confirms it in a layout effect, so the browser shows `0`, `1`, `2`. Ultima should key state styles on `data-panel-open` (Trigger) and `data-open` / `data-starting-style` / `data-ending-style` (Panel), which are the documented ones, and treat `data-orientation`, `data-hidden` and `data-value` as noise. Under the spec's axes rule, `orientation` is not an axis for Accordion: a deprecated prop that emits an attribute nothing reads is not a prop Ultima forwards.

### 4. What `--accordion-panel-width` is for

`useCollapsiblePanel` measures both `scrollHeight` and `scrollWidth` in `getDimensions` and returns them together; `AccordionPanel` writes both as inline custom properties, `auto` when unmeasured and `<n>px` after measurement, exactly as `CollapsiblePanel` writes `--collapsible-panel-height` and `--collapsible-panel-width` (`accordion/panel/AccordionPanel.mjs`, `collapsible/panel/CollapsiblePanel.mjs`). Nothing in Base UI reads the width variable back; its only reader is a consumer stylesheet that animates `width` for a panel that opens sideways. The shipped docs describe it as "The accordion panel's width." and every demo uses only the height variable. It has never been tied to `orientation`: the removed roving-focus code was the only thing that read `orientation`, and it never touched dimensions. The one animation-detection wrinkle: the closing branch of `useCollapsiblePanel` unmounts immediately if `nextDimensions.height > 0 || nextDimensions.width > 0` is false, so a width-animated panel is measured by the same code path. Ultima's Collapsible reads height only; Accordion inherits that decision and the width variable stays unused, which costs nothing because Base UI seeds it whether or not it is read. Base UI issue #3910 asks for a Collapsible `orientation` prop for horizontal opening and is still open with no maintainer answer; the width variable is what exists instead.

### 5. The Panel contract transfers whole

`AccordionPanel` and `CollapsiblePanel` both call the one `useCollapsiblePanel` from `collapsible/panel/useCollapsiblePanel.mjs` with the same ten parameters (`externalRef`, `hiddenUntilFound`, `id`, `keepMounted`, `mounted`, `onOpenChange`, `open`, `setMounted`, `setOpen`, `transitionStatus`), and `AccordionItem` gets those from the same `useCollapsibleRoot` that `CollapsibleRoot` uses, providing the same `CollapsibleRootContext`. So every piece of Collapsible's Panel contract holds by construction:

- `getAnimationType` calls `ownerWindow(element).getComputedStyle(element)` and branches on `animationName` plus `animationDuration` and on `transitionDuration`, through `hasNonZeroDuration`, which parses comma lists and needs any part `> 0`. `1ms` under reduced motion still passes.
- The warning text is shared and names both components: `'CSS transitions and CSS animations both detected on Collapsible or Accordion panel.'`, followed by `'Only one of either animation type should be used.'`; the transition wins.
- With `'none'` detected, the close path calls `setMounted(false)` in the same layout effect, so the panel unmounts on the same frame; on open it sets the dimensions and forces the panel status to `idle`.
- `hidden="until-found"` is forced through `setAttribute` in a layout effect and a `beforematch` listener opens the item with reason `none` and skips the next open's motion by temporarily zeroing `transition-duration` or `animation-duration`.
- The opening pass resets inline `justify-content`, `align-items`, `align-content`, `justify-items` to `initial !important` for measurement and restores them next frame, so a consumer's inline flex alignment on the panel does not distort `scrollHeight`.

Proof-bar item 8 therefore reads the same on `Accordion.Panel`: computed `transition-duration` not `0s`, `animation-name` `none`, and `display` not overridden while `[hidden]`. The `hiddenGuard` rule from `collapsible.tsx` (`':is([hidden]):not([hidden="until-found"])': { display: 'none' }`) is needed for the same reason.

Where Accordion's panel differs:

- **`role="region"` and `aria-labelledby`** on every panel, unconditionally (see 2). Collapsible's panel has no role and no label.
- **`hiddenUntilFound` and `keepMounted` resolve panel-first, then root.** `AccordionPanel` reads `hiddenUntilFoundProp ?? contextHiddenUntilFound` and `keepMountedProp ?? contextKeepMounted`, the context values being Root's props defaulted to `false`. Both are `Pick<AccordionRoot.Props, 'hiddenUntilFound' | 'keepMounted'>` in `AccordionPanel.d.ts`. Root warns in dev when `hiddenUntilFound` is set with `keepMounted={false}`; Panel warns when its own `keepMountedProp === false` and `hiddenUntilFound` is true from either level. The shipped docs: "It can be set on each `Accordion.Panel`, or once on `Accordion.Root` to apply to all panels." Collapsible has both props on Panel only.
- **`transitionStatus` in Panel state.** `AccordionPanelState extends AccordionItemState` and adds `transitionStatus: TransitionStatus`; the value is the panel-level status from the hook (`forcePanelIdle ? 'idle' : transitionStatus`), not the root's. It is what `data-starting-style` / `data-ending-style` are mapped from through `transitionStatusMapping`. Trigger's mapping is `triggerOpenStateMapping` alone, so an Accordion trigger never carries the transition attributes; Collapsible's trigger does carry them because its mapping spreads `transitionStatusMapping`, though its state has no `transitionStatus` key so they never render. Same visible result.
- **`data-index`** on Item, Header and Panel (documented) and Trigger (undocumented), from `useCompositeListItem` through `CompositeList`, the one composite piece Root kept. It is a string of the DOM-order index, `0`-based.
- **State shape.** `AccordionItemState` is `{ value, disabled, orientation, hidden, index, open }`; Panel adds `transitionStatus`. `CollapsiblePanel`'s state is `{ open, disabled, transitionStatus }`. A `className` or `style` function on an Accordion part sees `index` and can stripe rows without CSS.
- **Value is always an array, `multiple` or not.** `AccordionValue<Value> = Value[]`; `defaultValue` falls back to a shared frozen `EMPTY_ARRAY`. With `multiple` false, `handleValueChange` computes `value[0] === newValue ? [] : [newValue]`, so opening one item closes the other and clicking the open item empties the array. There is no "one must stay open" mode; the `eventDetails.cancel()` path (`details.isCanceled`) in `onValueChange` is how a consumer would refuse the empty array, the same shape the spec records for a single-selection Toggle Group under item 7. `Accordion.Item` also has its own `onOpenChange(open, eventDetails)`, called before the root's handler, with the same cancel gate. Items without a `value` prop get a generated id, which is why the v1.2.0 changelog says items "must have an explicit `value` set in order to be initially open".
- **Event reasons.** `AccordionRootChangeEventReason` is `'trigger-press' | 'none'`, `none` being the `beforematch` path.

### 6. `Header`, heading level, and the caret

**Base UI.** `AccordionHeader` is `useRenderElement('h3', ...)` with no level prop; `AccordionHeaderProps extends BaseUIComponentProps<'h3', AccordionHeaderState>` (`accordion/header/AccordionHeader.mjs`, `.d.ts`). The only way to change the level is `render={<h2 />}` (verified above: the rendered element is `<h2 … data-open="">` with all state attributes intact). The shipped docs have no heading-level prose or example; the Header section says only "Renders an `<h3>` element." The caret is consumer content: every demo puts `<PlusIcon className={styles.Icon} />` inside `Accordion.Trigger` and rotates it with `[data-panel-open] > & { transform: rotate(45deg) }` (CSS Modules) or `group-data-panel-open:rotate-45` (Tailwind). No Base UI accordion part renders an icon.

**Radix.** `AccordionHeader` renders `Primitive.h3` with `data-orientation` and `data-state`, no level prop; the docs say "Wraps an `Accordion.Trigger`. Use the `asChild` prop to update it to the appropriate heading level for your page." Same answer as Base UI, spelled `asChild` instead of `render`. The caret is consumer content: the docs example imports `ChevronDownIcon` from `@radix-ui/react-icons`, places it inside `Accordion.Trigger` with `aria-hidden`, and rotates it with `.AccordionTrigger[data-state="open"] > .AccordionChevron { transform: rotate(180deg) }`. Radix still ships the roving focus the APG dropped: `ACCORDION_KEYS = ['Home', 'End', 'ArrowDown', 'ArrowUp', 'ArrowLeft', 'ArrowRight']` and a `handleKeyDown` on the root switching on `orientation` and `dir`, and its docs table lists ArrowDown/Up/Right/Left, Home and End.

**React Aria Components.** There is no accordion component; `DisclosureGroup` wraps `Disclosure`s. The documented anatomy is `<Disclosure><Heading><Button slot="trigger" /></Heading><DisclosurePanel /></Disclosure>`, where `Heading` is the generic RAC `Heading` with `level` defaulting to `3` and rendering `h${level}` (`packages/react-aria-components/src/Heading.tsx`). So the level is a prop, `level={2}`, not a render swap. `Disclosure.tsx` has no arrow-key handling and no `Heading` of its own, only `ButtonContext` with a `trigger` slot; the panel role defaults to `'group'` with `'region'` opt-in, the reverse of Base UI's unconditional `region`. The caret is consumer content in the starter that the docs render: `DisclosureHeader` is `<Heading {...props}><Button slot="trigger" className="disclosure-button"><ChevronRight size={16} />{children}</Button></Heading>` with `lucide-react`'s `ChevronRight`, rotated 90° on `data-expanded`. The docs' Content section adds a rule Base UI's `<h3>` shares implicitly: "`<Heading>` and `<Button>` must not have interactive children."

**shadcn.** Both backends supply the glyph inside the trigger. The Radix file (`apps/v4/registry/new-york-v4/ui/accordion.tsx`) renders `<AccordionPrimitive.Header className="flex"><AccordionPrimitive.Trigger …>{children}<ChevronDownIcon className="pointer-events-none size-4 shrink-0 translate-y-0.5 text-muted-foreground transition-transform duration-200" /></AccordionPrimitive.Trigger></AccordionPrimitive.Header>` and rotates it with `[&[data-state=open]>svg]:rotate-180` on the trigger. The Base UI file (`apps/v4/registry/bases/base/ui/accordion.tsx`) imports `@base-ui/react/accordion` and renders two `IconPlaceholder`s (`ChevronDownIcon` hidden under `group-aria-expanded/accordion-trigger:hidden`, `ChevronUpIcon` shown under `group-aria-expanded/accordion-trigger:inline`), swapping rather than rotating, keyed on `aria-expanded` rather than `data-panel-open`. In both, `AccordionTrigger` wraps `Header` and `Trigger` into one export with the `Header` fixed to its primitive default (`<h3>`), no level prop, and no way through to `asChild` / `render` on the header without editing the file.

**What that decides for Ultima.** The three primitives agree: the heading is `<h3>` by default, changed by the consumer (`render`, `asChild`, or `level`), and the caret is the consumer's glyph inside the button. Only shadcn treats the caret as a supplied part, and it pays for that by fusing `Header` and `Trigger` into one component and pinning the heading level. Ultima's Collapsible contract already reads "a caret is the consumer's glyph, rotating on `data-panel-open`" and "no glyph slot", and Accordion's trigger is the same `useButton` with the same `data-panel-open`. The glyph-slot rule does not reach Accordion. The one new decision Accordion forces is the heading: `Header` should pass through so `render={<h2 />}` works, the docs should say the level is the consumer's and defaults to `h3`, and no Ultima wrapper should fuse `Header` into `Trigger` the way shadcn does, because that is the move that loses the level. The APG's "the button element is the only element inside the heading element" is the constraint the docs page should print next to the caret example, so the caret goes inside `Trigger`, never beside it.

### Facts later tickets will need

- Accordion keyboard = native button + Tab. No `onKeyDown` anywhere in `accordion/`. Item 7 has no candidate.
- `orientation` and `loopFocus` are deprecated no-ops since v1.6.0 (#4965). Ultima's `AccordionRootProps` should `Omit` both; `data-orientation` renders everywhere and nothing reads it.
- Undocumented attributes: `data-hidden` (all four item-level parts while closed), `data-closed` (Item and Header too), `data-value` on Trigger, `data-index` on Trigger. Style on `data-panel-open`, `data-open`, `data-starting-style`, `data-ending-style` only.
- `Accordion.Panel` = `Collapsible.Panel` + `role="region"` + `aria-labelledby`, unconditional; the APG says avoid `region` past about six panels and Base UI gives no switch.
- `hiddenUntilFound` / `keepMounted`: Panel prop wins, then Root, then `false`. Ultima's Collapsible sets neither; Accordion should set neither.
- The panel CSS contract and proof-bar item 8 transfer unchanged; the variable is `--accordion-panel-height`, not `--collapsible-panel-height`. `--accordion-panel-width` is seeded and unread.
- `value` is always an array; `multiple={false}` toggles `[x]` / `[]`; the cancel gate is `eventDetails.cancel()` in `onValueChange` or `Item.onOpenChange`.
- `Header` is `<h3>`, level via `render` only; no glyph slot; caret inside `Trigger`; APG requires the button to be the heading's only child.
- Prior art: Radix still implements arrow keys; React Aria never did (and defaults the panel to `group`); shadcn supplies the chevron by fusing Header into Trigger.
