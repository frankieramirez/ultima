# What can replace Base UI for custom elements, graded by the four things ADR 0002 names

## Findings

**Verdict: none of the candidates passes the ADR 0002 test.** The test, read from `docs/adr/0002-base-ui-primitives.md`, is that a primitive layer supplies focus management, keyboard behavior, and ARIA wiring (roles and state) and is unstyled. The candidates split cleanly into two groups. The ones that supply the four (Lion, generic-components, Spectrum Web Components, Shoelace, Web Awesome, Vaadin) all render CSS of their own and all require shadow DOM. The ones that render nothing (Lit alone, the Popover API and anchor positioning, ElementInternals) supply at most two of the four, and nothing at all for Tabs. The closest miss is generic-components' `generic-tabs`: 1.7 KB gzipped, no dependencies, correct roles, keyboard and roving tabindex, but it ships a `gap: 0.5rem` on the tablist inside a mandatory shadow root and has no tooltip. Lion is the closest full-coverage miss: white-label by policy, correct ARIA on both Tabs and Tooltip, but `LionTabs` bolds the selected tab and `LionTooltip` pulls in Popper.js for 24 KB gzipped.

One library outside the ticket's list does pass on paper: Zag.js's vanilla adapter (`@zag-js/vanilla`, MIT). Its tabs machine emits `role="tablist"|"tab"|"tabpanel"`, `aria-selected`, `aria-controls`, `aria-labelledby`, arrow keys with `loopFocus` and an `activationMode`; its tooltip machine emits `role="tooltip"`, `aria-describedby`, `Escape`, `openDelay`/`closeDelay`. It renders no DOM and no CSS. It is not an element base: it hands back attribute bags to spread onto elements you render, so Ultima would still write the custom element, and its docs headline React, Solid and Vue only. It costs 12 KB gzipped for tabs and 22 KB for tooltip. It is the one lead worth a follow-up ticket; this note does not grade it further because it was not in scope and it is not a web-component library.

If Ultima hand-rolls, the layer owns everything in section 5 below. For Tooltip the platform can take a real share (top layer, Escape, light dismiss, anchor positioning everywhere; hover, focus and the description mapping in Chromium 142+ only). For Tabs the platform gives nothing; the whole APG contract is Ultima's.

### 1. The bar: what Base UI actually gives Ultima's Tabs and Tooltip

Graded against the installed copy, `@base-ui/react` 1.8.0, because that is what Ultima's `packages/ui/src/tabs.tsx` and `tooltip.tsx` import.

**Tabs.** `TabsList` renders `role="tablist"` and `aria-orientation="vertical"` when vertical. `TabsTab` renders `role="tab"`, `aria-controls` (the panel id), `aria-selected`, and delegates focus to the composite system (`useCompositeItem`), which handles `ArrowLeft`/`ArrowRight`/`ArrowUp`/`ArrowDown`, `Home`, `End`, with `loopFocus` defaulting to true and `activateOnFocus` defaulting to false. `TabsPanel` renders `role="tabpanel"`, `aria-labelledby` (the tab id), and `hidden` when not mounted. Styling hooks are data attributes (`data-active`, `data-orientation`, `data-disabled`, `data-hidden`, `data-activation-direction`) and the Indicator's `--active-tab-*` CSS variables. No CSS is rendered. So Base UI's Tabs supplies all four.

**Tooltip.** `TooltipTrigger` wires `useHoverReferenceInteraction` (mouse-only hover with open and close delays, safe polygon) and `useFocus`. `TooltipPopup` spreads `FOCUSABLE_POPUP_PROPS`, which is exactly `{ tabIndex: -1, [FOCUSABLE_ATTRIBUTE]: '' }`. There is no `role="tooltip"` and no `aria-describedby` anywhere in Base UI's tooltip directory. Ultima adds the role itself (`tooltip.tsx` line 78: `<BaseTooltip.Popup role="tooltip" ...>`) and requires `aria-label` on the trigger by type (`tooltip.tsx` line 64), which follows Base UI's own guidance that tooltips are supplementary and the trigger must carry `aria-label`. So for Tooltip, Base UI supplies keyboard (focus opens, Escape closes), focus management (the popup is not a tab stop), and positioning; the roles and ARIA are already Ultima's. The bar for a Tooltip replacement is therefore lower than the ADR's wording suggests, and the hand-rolled list in section 5 reflects that.

### 3. Candidate notes

**Lit alone.** Lit's own pitch is "around 5 KB (minified and compressed)"; measured 6.2 KB. It provides a base class, templating, reactive properties and scoped styling, and no components or accessibility helpers. Shadow DOM is the default render root; the docs show `createRenderRoot() { return this; }` for light DOM and warn: "Rendering into children and not shadow DOM is generally not recommended. Your element will not have access to DOM or style scoping, and it will not be able to compose elements into its internal DOM." Grade: zero of four, no styles. A rendering base, not a primitive layer.

**Lion.** ING's Lit-based set: "an unopinionated, white-label layer", demos "only come with functional stylings". `LionTabs` renders a shadow root with `role="tablist"` on an inner div and two slots; it writes `role="tab"`, `aria-controls`, `aria-selected`, `tabindex` 0/-1 and an id onto the light-DOM tab children, and `role="tabpanel"`, `aria-labelledby`, `tabindex="0"` and an id onto the panels; arrows, Home and End wrap; roving tabindex; a `selected` boolean attribute on tab and panel. Its static styles are four rules: `.tabs__tab-group { display: flex }`, `::slotted([slot='tab'][selected]) { font-weight: bold }`, panels `display: none` / `display: block` by `[selected]`. The bold rule is a visual opinion, so Lion fails "renders no styles" by one declaration. `LionTooltip` is `ArrowMixin(OverlayMixin(LitElement))` with `withTooltipConfig`: `placementMode: 'local'`, `hidesOnEsc: true`, `handlesAccessibility: true`, `isTooltip: true`, `invokerRelation: 'description'` (or `'label'`), plus `withHoverInteraction` which attaches `focusin`/`focusout` on the invoker and `mouseenter`/`mouseleave` on invoker and content with `delayIn: 0`, `delayOut: 300`. `OverlayController` sets `aria-describedby` (or `aria-labelledby`) on the invoker and `role="tooltip"` on the content node, wraps content in a native `<dialog role="none">`, and positions with `@popperjs/core` ^2.11.8. Popper is why one tooltip is 24 KB. Exposure is attributes and slots; no `part=`, no `:state()`.

**generic-components.** Pascal Schilp's `@generic-components/components`: plain `HTMLElement`, no runtime dependencies, ten components, no tooltip. `GenericTabs` attaches an open shadow root whose template is a default slot, `<div part="tablist" role="tablist"><slot name="tab">` and `<div part="panel"><slot name="panel">`; the stylesheet is `:host { display: block }`, `:host([vertical]) { display: flex }`, `div[role="tablist"] { display: flex; gap: 0.5rem }` and a column rule for vertical. Roles, `aria-selected`, `tabindex`, `aria-controls`, `role="tabpanel"`, `aria-labelledby` are written onto the slotted light-DOM children in `update()`; `SelectedMixin` handles arrows by orientation, Home, End, wraps, and moves focus; selection follows focus (`activateOnKeydown: true`); Enter and Space are not handled. Grade: four of four for Tabs at 1.7 KB, but a layout opinion (`gap`) in a mandatory shadow root, and nothing for Tooltip.

**Spectrum Web Components.** Adobe's Lit implementation of Spectrum; `SpectrumElement extends LitElement`, every element renders a shadow template. Styles are the design system: `tab.css.js` sets `color`, `cursor`, `block-size` and a `transition` from `--spectrum-tabs-*` tokens. `Tabs` uses `RovingTabindexController` (direction `both`, `elementEnterAction` selects when `auto` is set), Enter/Space select, `role="tablist"` with `part="tablist"` in the shadow root, `aria-orientation="vertical"`, and `managePanels` writes `aria-controls` / `aria-labelledby` between light-DOM `sp-tab` and `sp-tab-panel`. `Tab` sets `role="tab"`, `aria-selected`, `tabindex` 0/-1, `aria-disabled`, and reflects `selected`. `sp-tooltip` in `self-managed` mode walks up to the first ancestor matching `focusableSelector`, dynamically imports `sp-overlay` (type hint), and `HoverController` adds the overlay id to the trigger's `aria-describedby` and closes on Escape; positioning is `@floating-ui/dom` 1.7.4. `Tooltip.js` itself renders only an `aria-hidden` tip span and sets no `role`. Grade: four of four for Tabs, styled, shadow-only, 18 KB; Tooltip 40 KB with the overlay stack inlined.

**Shoelace and Web Awesome.** Both MIT, both Lit, both shadow-only, both styled (`tab.styles.js` plus `component.styles.js`; documented custom properties `--indicator-color`, `--track-color`, `--track-width`). `sl-tab-group`: `role="tablist"` on the shadow div `part="tabs"`; `sl-tab` sets `role="tab"`, `aria-selected`, `aria-disabled` on its host and reflects `active`; `sl-tab-panel` sets `role="tabpanel"`; `setAriaLabels()` writes `aria-controls` and `aria-labelledby`; `handleKeyDown` covers arrows (RTL-aware), Home, End, Enter and Space; roving tabindex; `activation` auto or manual. `sl-tooltip` wraps `sl-popup` (Floating UI); the body has `role="tooltip"` and `aria-live="polite"` while open; triggers `hover focus` (default), `click`, `manual`; delays from `--show-delay`/`--hide-delay`; Escape on a document keydown listener. Web Awesome's base class attaches `ElementInternals` and exposes `customStates` backed by `internals.states` (docs: `wa-checkbox:state(checked)`), but `wa-tab` exposes `active` and `disabled` as reflected attributes only. `wa-tooltip` finds its anchor by `for` through `rootNode.getElementById`, uses `wa-popup` (Floating UI), and deliberately uses `aria-labelledby` ("aria-describedby usually in some screen readers is required to be on the actually focusable element, whereas with aria-labelledby it'll still read on first focus"). The free `webawesome` package is MIT; `webawesome-pro` is paid. Grade: four of four for both components, styled, shadow-only; Shoelace 17 to 20 KB, Web Awesome 24 to 38 KB.

**Vaadin.** Apache-2.0 for the 60-plus core components, Vaadin Commercial License for the six Pro ones. `Tabs extends TabsMixin(ElementMixin(ThemableMixin(PolylitMixin(LumoInjectionMixin(LitElement)))))`; `TabsMixin extends ResizeMixin(ListMixin)`; `ListMixin` gets arrows and Home/End from `KeyboardDirectionMixin`, adds type-ahead, roving tabindex, `aria-orientation`; selection is set on click, not on focus. `vaadin-tab` sets `role="tab"` and exposes `disabled`, `focused`, `focus-ring`, `selected`, `active`, `orientation`, `has-tooltip` as host attributes. The base stylesheet is layout plus `--vaadin-*` variables (`--vaadin-tab-text-color`, `--vaadin-tab-background`), and Lumo or Aura is injected on top, so it is styled by design. `vaadin-tooltip` targets an element by `for`, sets `aria-describedby` on it, `role="tooltip"` on the content, opens on hover and on keyboard focus only (`isKeyboardActive()`), 500 ms focus/hover/hide delays, Escape closes, and positions with its own `PopoverPositionMixin`. Grade: four of four, styled, shadow-only, and the heaviest of the set at 27 and 53 KB.

**Ionic and Stencil.** Stencil (MIT) is a compiler; its component options are `shadow: true` (falls back to scoped), `shadow: { delegatesFocus }`, `scoped: true`, and `formAssociated: true` for `ElementInternals`; styling docs cover `::part()` and `:host` custom properties and say nothing about custom states. Ionic's `ion-tabs` is a `NavOutlet` router container, not an APG tabs widget. `ion-tab-bar` is `shadow: true`, `role="tablist"`, iOS and MD stylesheets. `ion-tab-button` renders `<a part="native" role="tab" aria-selected>`, handles Enter and Space in `onKeyUp`, and has no arrow-key or `aria-controls` handling. `ion-segment` / `ion-segment-button` also emit `tablist` / `tab`. There is no tooltip component in `@ionic/core`'s component directory. Grade: a styled app framework; not a primitive layer.

**Popover API and CSS anchor positioning.** The HTML spec's `popover` attribute has three states: `auto` ("closes other popovers when opened; has light dismiss and responds to close requests"), `hint` ("closes other hint popovers when opened, but not other auto popovers; has light dismiss and responds to close requests"), `manual`. Popovers go to the top layer. The spec sets no ARIA: "authors should use the appropriate ARIA attributes to ensure the popover is accessible", and its menu example notes that "navigating the menuitems with arrow keys and activation behaviors would still need author scripting". The show-popover algorithm does "set element's implicit anchor element to source", so a popover opened through `popovertarget` or `showPopover({ source })` anchors to its invoker with no `position-anchor`. The UA stylesheet is not empty: `[popover] { position: fixed; inset: 0; width: fit-content; height: fit-content; margin: auto; border: solid; padding: 0.25em; overflow: auto; color: CanvasText; background-color: Canvas }`, which Ultima's surface recipe would have to reset. Support: `popover` Chrome 114, Firefox 125, Safari 17. Anchor positioning by property: `anchor-name` Chrome 125, Firefox 147, Safari 26; caniuse's umbrella entry rates Chrome 151 and Safari 27 as the first "full" versions and Firefox 147 through 159 as partial, so the level-1 core is usable now and the fallback extras are not yet everywhere. Interest invokers (`interestfor` on `button`, `a[href]`, `area`) add the hover and focus half of a tooltip: `interest-delay-start` / `interest-delay-end` default 0.5 s, Escape dismisses, long-press context menu on touch, and for "plain hints" the browser exposes the popover's content as the invoker's accessible description, which is the `aria-describedby` mapping done by the UA. It shipped in Chrome 142 (October 2025); WebKit's position is "we therefore remain opposed to this feature" and Mozilla's is "defer". So the platform can carry Tooltip's positioning, layering, Escape and light dismiss in all three engines today, and its hover, focus and description mapping in Chromium only. It carries nothing for Tabs.

**ElementInternals.** `static formAssociated = true` plus `attachInternals()` gives `setFormValue`, `setValidity`, `form`, `labels`, and the form lifecycle callbacks; that is Button's form participation. `internals.states` is a `CustomStateSet` matched by `:state(name)` (Chrome 125, Firefox 126, Safari 17.4). `ElementInternals` carries `ARIAMixin`, so `internals.role = 'tab'` and `internals.ariaSelected = 'true'` set semantics without reflecting attributes; MDN: "these are included in order that default accessibility semantics can be defined on a custom element. These may be overwritten by author-defined attributes" (Chrome 103, Firefox 119, Safari 16.4; the interface itself Chrome 77, Firefox 93, Safari 16.4). It supplies no keyboard handling and no focus management. One constraint matters for Tabs: IDREF attributes such as `aria-controls` and `aria-labelledby` "can only refer to elements in the same node tree", which is why every library above writes the tab and panel ARIA onto light-DOM slotted children rather than into a shadow root. Reference Target (`shadowrootreferencetarget`, `ShadowRoot.prototype.referenceTarget`) forwards `label for`, `aria-labelledby`, `popovertarget` and `commandfor` into a shadow root, but it shipped in Chrome 152 only. Grade: roles and ARIA state, no styles, no keys, no focus; two of four.

### 4. Why the shadow DOM column matters for StyleX

ADR 0001 makes StyleX the only styling engine, and StyleX emits one document-level stylesheet of atomic classes. Lit's docs are explicit that a shadow root scopes styles, so a document stylesheet does not reach a shadow tree, and a shadow-rendered element would need the StyleX output adopted into every root (or the parts exposed through `::part()` and styled from outside, which loses the class-name model). Every library candidate requires shadow DOM. A hand-rolled layer that renders into light DOM (Lit's `createRenderRoot(){ return this }`, or a bare `HTMLElement`) lets StyleX class names land on the element exactly as they do in React, at the cost Lit names: no slot composition and no scoping. This is the structural reason the libraries fail for Ultima even before the styles column, and it is why the hand-rolled list below assumes light DOM.

### 5. What a hand-rolled layer would own

Priced against APG and against what Base UI does today. "Platform" marks what the browser can carry.

**Tabs** (APG Tabs pattern; nothing from the platform):
- Roles: `tablist` on the list, `tab` on each tab, `tabpanel` on each panel; `aria-orientation="vertical"` when vertical.
- ARIA state and wiring: `aria-selected` true/false, `aria-controls` tab to panel, `aria-labelledby` panel to tab, stable ids for both, `aria-disabled`, `hidden` on inactive panels, `aria-label` or `aria-labelledby` on the tablist (Ultima's prop contract).
- Keyboard: Left/Right (Up/Down when vertical, mirrored in RTL), wrap at the ends (Base UI `loopFocus` default), Home and End, Enter and Space to activate in manual mode, an `activateOnFocus` option (Base UI defaults to manual; APG recommends automatic when panels render without latency), skip disabled tabs.
- Focus management: roving tabindex (active tab 0, others -1, and keep 0 on an enabled tab when the selected tab is disabled, as Base UI does), Tab key leaves the tablist, panel is a tab stop when it holds no focusable content (Lion sets `tabindex="0"` on panels).
- State exposure for StyleX: the Base UI attribute set (`data-active`, `data-orientation`, `data-disabled`, `data-hidden`, `data-activation-direction`) or `:state()`; Indicator needs the `--active-tab-*` measurements if the underline variant keeps its animated indicator.
- Structure: tab and panel elements must live in one tree for the IDREFs, so either both are light-DOM children of the root or the layer skips ids and sets relationships by element reference where the engine supports it.

**Tooltip** (APG Tooltip pattern, marked "work in progress"; Base UI's own stance is that the trigger carries `aria-label` and the tooltip is supplementary):
- Roles and ARIA: `role="tooltip"` on the popup (Ultima already sets this over Base UI), and either `aria-describedby` from trigger to popup (APG, Lion, Vaadin, SWC, Shoelace) or the `aria-label`-on-trigger contract Ultima uses now. Platform: Chromium 142+ maps a plain-hint `interestfor` target as the invoker's description with no attribute.
- Open and close: hover with open delay and close delay and a hoverable popup (Base UI: `delay` 600 ms, Provider `timeout` 400 ms shared across triggers, `disableHoverablePopup`), mouse-only hover so touch never opens it, focus opens and blur closes, Escape closes, click on the trigger closes. Platform: `popover="hint"` gives light dismiss, Escape as a close request, and the hint stack that lets a tooltip sit over an open `auto` popover; `interestfor` gives hover, focus and the delays in Chromium only, so a JS fallback stays for Firefox and Safari.
- Focus management: the popup is never a tab stop (`tabIndex: -1`), focus stays on the trigger, and nothing inside is interactive.
- Positioning: side, align, offsets, collision flipping and shifting, and the `--anchor-width`/`--positioner-width`/`--transform-origin` variables Ultima's styles read. Platform: implicit anchor from the invoker plus `position-area` and `position-try-fallbacks` (Chrome 125, Firefox 147, Safari 26); otherwise `@floating-ui/dom` at 8.5 KB gzipped, which is what Shoelace, Web Awesome and SWC ship.
- Layering: top layer through `popover` instead of Ultima's portal and z-index constant; reset the UA `[popover]` border, padding and background in the surface recipe.
- State exposure: `data-open`, `data-closed`, `data-side`, `data-align`, `data-anchor-hidden`, or `:state()` equivalents.
