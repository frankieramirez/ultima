# When one trigger fires an anchored toast several times, do Base UI, Sonner and Mantine replace, stack or dedupe?

## Findings

None of the three dedupes on its own. A repeat call without an `id` adds a new toast in all three. Each library dedupes only when the caller passes the same `id`, and they handle a reused id differently: Base UI and Sonner update the live toast in place, while Mantine ignores the second `show` call. Only Base UI anchors a toast to an element. Sonner and Mantine offer six fixed screen positions and nothing more. For a repeated "Copied" confirmation, Base UI's own anchored demo avoids repeats altogether: it disables the trigger while the toast is up. Its deduplicate demo shows the other documented route, which is to reuse a fixed `id`.

### Base UI (`@base-ui/react`, Ultima pins 1.8.0, latest 1.9.0)

- **Anchoring.** You pass `positionerProps.anchor` to `add()`, and each toast renders in its own `<Toast.Positioner>` [1][2]. The docs pitch this for "transient 'Copied' toasts that appear near the button that triggered the action" [1]. They also say anchored toasts belong in a separate `<Toast.Provider>` from stacked ones, each with its own `createToastManager()` [1].
- **The anchored demo on repeat clicks.** It calls `anchoredToastManager.add({ description: 'Copied', positionerProps: { anchor, sideOffset: 10 }, timeout: 1500, onClose() { setCopied(false) } })` with no `id`. It sets `copied` to true on click and renders the trigger as `<Button disabled={copied} focusableWhenDisabled>`, swapping the clipboard icon for a check [2]. A second click cannot fire while the toast is visible, so the demo never shows two anchored toasts. The copy of the docs bundled in the 1.8.0 package uses the same pattern, with a Tooltip that is also disabled while `copied` is true [7].
- **The anchored demo's CSS has no collapsed-stack rules.** It has no `data-behind`, no `data-expanded`, no `data-limited` and no `--toast-frontmost-height`. The only index-aware rule is `z-index: calc(1000 - var(--toast-index))` on the Positioner, which puts the newest toast on top [3]. If two anchored toasts did exist, both would keep their text, and the newer one would paint over the older at the same anchor.
- **`data-behind` exists for the stacked deck.** `<Toast.Content>` sets `behind = visibleIndex > 0` [4]. Ending toasts get `visibleIndex` −1, and every other toast counts up from 0 newest-first [5]. The docs pair it with `--toast-frontmost-height`: "`<Toast.Content>` is used to hide the content of the toasts behind it", with `.ToastContent[data-behind] { opacity: 0 }` and `.ToastContent[data-expanded] { opacity: 1 }` [1]. That guidance sits under the stacked styling section, and the varying-heights example repeats it [1]. The attribute carries no anchored check, so an anchored toast that is not the newest also gets `data-behind`.
- **`limit`.** The default is 3 [6]. "When the limit is exceeded, the oldest toasts are marked as `limited` (via the `data-limited` attribute) rather than removed" [6]. `applyLimited` flags every active toast past the newest `limit` [5]. A limited toast stays mounted with `inert` [1][8].
- **Id reuse.** "If you pass an `id` that already exists, the existing toast is updated in place instead of creating a duplicate" [1]. In `addToast`, an existing non-ending toast with that id goes through `updateToastInternal(id, updates, resetTimer = true, markUpdated = true)`, so its text is replaced, its timer restarts and `updateKey` goes up by one. If the matching toast is already ending, Base UI removes it and adds a fresh toast [5]. The 1.8.0 build has the same branch [7]. `toastManager.update(id, …)` changes an existing toast without re-adding it [1]. The deduplicate demo calls `add({ id: 'save-status', … })` on every click and reads `updateKey` to replay a pulse animation on the toast that is already mounted [1][9].

### Sonner (shadcn/ui's toast; `sonner` 2.0.8)

- **No anchoring.** `position` is one of six screen corners or edges, set on `<Toaster>` or per toast, and toasts with different positions form separate stacks [10][12][14]. shadcn/ui's `Toaster` passes its props straight through to Sonner's [15].
- **Repeats stack.** Each call without an `id` gets the next counter id [11], and the Toaster puts the new toast at the front (`[toast, ...toasts]`) [12].
- **Behind toasts lose their text while collapsed.** `data-front` is true only at index 0, and `data-visible` is `index + 1 <= visibleToasts` (default 3) [12]. A collapsed toast that is not at the front is clamped to `--front-toast-height` and scaled [13]. On a styled toast, `[data-expanded='false'][data-front='false'][data-styled='true'] > *` sets its children to `opacity: 0` [13]. Toasts past `visibleToasts` get `opacity: 0; pointer-events: none` [13]. `data-styled` is false for `toast.custom()` JSX and for unstyled toasts, so those keep their content visible behind the front [12]. Hovering expands the stack, and `expand` (default false) keeps it open [14].
- **Id reuse updates.** If a toast with that id exists and was not dismissed, `create` merges the new options and title into it and publishes the result. If the old toast was dismissed, Sonner drops it and creates a new one [11]. The Toaster replaces the toast at the same index [12]. The new toast object re-runs the auto-close effect, which clears the timeout and starts a new one from `remainingTime`. That value only shrinks when the toast pauses, so an update usually restarts the full duration [12]. The author's guide says: "calling `toast()` again with the same `id` updates the existing toast" [14]. Its fix for a toast that "appears twice" includes "pass a stable `id` so the second call updates rather than duplicates" [14].

### Mantine Notifications (`@mantine/notifications` 9.7.3)

- **No anchoring.** `position` takes the same six screen positions, per call or on `<Notifications>` [16][17].
- **Repeats stack as a list by default.** Each notification without an id gets a `randomId()` and is appended [16]. With the default layout every notification stays fully visible with its own text [17][19]. `limit` defaults to 5. "All notifications added after the `limit` was reached are added to the queue and displayed when a notification from the current state is hidden" [16][17]. `priority` can move a visible notification back into the queue [17].
- **`layout="stacked"`** shows "only the latest notification … fully visible, and older notifications peek out behind it" [17]. The notifications behind are scaled and offset, up to four layers deep. Mantine does not fade their content, but it makes them inert and pauses their auto-close timers while the stack is collapsed [17][18][19].
- **Id reuse is a no-op on `show`.** `showNotification` returns the state unchanged when a notification with that id already exists, so the second call's text is dropped and the first one's timer keeps running [16]. To change the text you call `notifications.update({ id, … })`, which merges into the existing entry in the visible state or the queue [16][17]. The auto-close effect depends on `[autoCloseDuration, active, dismissed]`, so an update that leaves `autoClose` alone does not restart the timer [18].

### Ultima today

`packages/ui/src/toast.tsx` styles anchored and stacked toasts with one set of rules. `ANCHORED = ':is([data-side] > *)'` matches a Root inside a Positioner. The Root rules switch an anchored toast to `position: relative`, `height: auto`, `transform: none` and `width: max-content` (lines 21, 85–112). The Content rule has no anchored exception: `opacity: 0` on `[data-behind]`, back to 1 on `[data-behind][data-expanded]` (lines 120–124). Each anchored toast that is not the newest therefore keeps its frame, fill, border and shadow but shows no text, until the pointer or focus expands the viewport. The Root rule `[data-limited] → opacity: 0` (line 93) also applies to anchored toasts, so with Base UI's default `limit` of 3 the fourth-newest one disappears. Ultima's docs list the anchored parts and give no example (`apps/docs/src/content/components/toast.mdx`, "Anchored toasts"). Base UI's anchored demo includes neither rule [3].

### Comparison

| | Base UI anchored Toast | Sonner | Mantine Notifications |
| --- | --- | --- | --- |
| Anchors to an element | Yes, `positionerProps.anchor` | No, six screen positions | No, six screen positions |
| Repeat call, no id | New toast; anchored ones overlap at the anchor | New toast at the front of the stack | New notification appended, or queued past `limit` |
| Repeat call, same id | Updates in place, restarts the timer, bumps `updateKey` | Updates in place, timer restarts | `show` ignored; `update` needed; timer not restarted |
| Earlier toasts' text | Hidden only if your CSS adds the `data-behind` rule; the anchored demo does not | Hidden (`opacity: 0`) while collapsed, shown on hover | Visible in the default list; occluded but not faded in `stacked` |
| Overflow | `limit` 3; oldest get `data-limited` and `inert`, stay mounted | `visibleToasts` 3; extras `opacity: 0`, no pointer events | `limit` 5; extras wait in a queue |
| Docs pattern for a repeated confirmation | Anchored demo disables the trigger while visible; deduplicate demo reuses a fixed `id` | Reuse a stable `id` | Reuse an `id` with `update` |

**What the sources recommend for repeat anchored confirmations.** Keep at most one confirmation per trigger. Base UI's anchored demo does this by disabling the trigger (`disabled={copied}`, `focusableWhenDisabled`, re-enabled from `onClose`) and showing the confirmed state on the trigger itself [2]. Its deduplicate demo, together with Sonner's and Mantine's id APIs, shows the alternative: give each trigger a fixed `id`, so a repeat updates the toast already on screen. In Base UI and Sonner the repeat also restarts its timer; Mantine's `notifications.update` leaves the first timer running unless `autoClose` changes. In Base UI you can replay a pulse from `updateKey` [1][9][14][16][18]. None of the sources hides the content of an anchored toast behind a newer one. Base UI documents `data-behind` content hiding only for the collapsed stacked deck [1][3].
